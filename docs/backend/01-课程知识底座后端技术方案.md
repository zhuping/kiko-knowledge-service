## 1. 方案摘要

课程知识底座后端采用：

> 独立部署的模块化单体 FastAPI 服务 + 独立 MySQL 数据库 + Celery/Redis 异步判断任务。

首期不使用微服务集群、图数据库、Kafka、独立向量数据库或新的工作流引擎。

服务包含两个逻辑平面：

1. 管理平面：知识包、课程目录、教学目标、样题、反馈、审核和版本发布；
2. 数据平面：题目判断、教学目标查询、范围判断和调用方反馈 API。

两者使用同一代码仓库、同一应用镜像和同一数据库，通过路由、权限和领域模块隔离。

当前学习产品继续负责：

- 用户和孩子档案；
- 图片上传与 OCR；
- 题目确认；
- 学生学习进度；
- 最终业务范围和生成权限；
- 错题、变式题、PDF 和掌握反馈。

知识底座只返回：

- 教学目标匹配；
- 匹配类型；
- 相对于调用方课程上下文的范围状态；
- 教材证据；
- 知识包与判断器版本。

两个系统之间不共享数据库、不建立跨库外键、不使用分布式事务。

## 3. 当前后端现状与复用边界

### 3.1 当前可直接复用的技术能力

当前 `kiko-backend` 已具备：

- FastAPI 路由和 OpenAPI；
- Pydantic 2 请求、响应和 Provider Schema；
- SQLAlchemy 2 同步 Session；
- Alembic 数据库迁移；
- MySQL 和 SQLite 测试支持；
- Celery/Redis 任务和恢复扫描；
- ULID；
- 统一 `data/request_id` 响应；
- 统一 `error.code/message/details/request_id` 错误；
- JWT 和 Bearer Token 处理；
- OSS 私有对象存储；
- 结构化日志；
- Ruff、pytest 和覆盖率门禁；
- API → Domain Service → Repository/Provider/Model 的分层。

新服务沿用这些模式和依赖版本，不引入第二套后端风格。

### 3.2 当前课程与匹配数据的处理

当前表和新服务的归属如下：

| 当前对象 | 新服务处理 | 说明 |
|---|---|---|
| `curriculum_versions` | 迁移为知识包及发布版本 | 新服务成为权威来源 |
| `curriculum_chapters` | 迁移为课程节点 | 支持任意层级 |
| `knowledge_points` | 迁移为教学目标 | 使用稳定逻辑ID和版本修订 |
| `knowledge_point_prerequisites` | 迁移为目标关系 | 增加等价、拆分、合并等关系 |
| `knowledge_point_keywords` | 转换为匹配提示或任务特征 | 不继续作为唯一判断依据 |
| `question_templates` | 留在当前后端 | 属于变式题生成能力 |
| `knowledge_match_tasks` | 当前后端保留兼容记录 | 保存外部 classification_id 和结果快照 |
| `knowledge_match_candidates` | 当前后端保留兼容候选 | 由知识服务结果填充 |
| `scope_check_records` | 当前后端保留 | 最终生成权限依赖孩子状态 |
| `wrong_questions` | 当前后端保留 | 属于学习产品业务 |

### 3.3 不直接搬迁当前匹配实现

当前 `app/domains/matching/service.py` 使用数学题型模板、关键词、运算符、数字范围和当前学习范围进行规则评分。它适合当前数学 MVP，但不适合作为跨学科知识服务核心。

新服务复用其以下原则：

- 确定性候选召回；
- 保存候选和分项信息；
- 低置信度要求人工确认；
- 最终结果必须经过程序校验；
- 数据库任务状态是唯一事实来源。

不复用其数学专属规则和生成模板依赖。

## 4. 总体技术架构

### 4.1 部署拓扑

```text
教研管理后台
      │ HTTPS / SSO
      ▼
┌───────────────────────────────────┐
│ Kiko Curriculum Knowledge Service │
│                                   │
│  FastAPI                          │
│  ├─ Admin API                     │
│  ├─ Client API                    │
│  ├─ Catalog Domain                │
│  ├─ Release Domain                │
│  ├─ Classification Domain         │
│  ├─ Feedback Domain               │
│  └─ Audit Domain                  │
└───────┬─────────────┬─────────────┘
        │             │
        ▼             ▼
   MySQL 8.0      Redis / Celery
                        │
                        ▼
              Classification Worker
                        │
                        ├─ 模型 Provider
                        └─ OSS 私有教材资源

Kiko 当前后端
      │ HTTPS + Service Token
      └─────────────────────────────► Client API
```

### 4.2 进程划分

| 进程 | 职责 |
|---|---|
| `api` | 管理 API、客户端 API、查询、任务创建、反馈、发布事务 |
| `worker-classification` | 候选召回、模型比较、结果校验、范围计算和结果落库 |
| `worker-maintenance` | 超时任务恢复、过期数据清理、待回归任务扫描 |
| `beat` | 周期触发恢复和维护任务 |

首期使用同一应用镜像，通过启动命令和 Celery 队列区分进程。

### 4.3 数据事实来源

- MySQL 是知识内容、发布版本、判断状态和审核状态的唯一事实来源；
- Redis 只作为 Celery Broker、临时限流和短期缓存；
- Celery Result Backend 不作为业务状态查询来源；
- OSS 只保存受权教材媒体，数据库保存对象 key 和授权信息；
- 调用方题目原图默认不复制到知识服务 OSS。

### 4.4 服务独立性

知识服务必须能够：

- 独立部署；
- 独立扩容；
- 独立发布知识包；
- 独立回滚；
- 在当前产品不可用时继续服务其他调用方；
- 在知识服务不可用时不阻断当前产品保存题目。

| 层级 | 选择 | 说明 |
|---|---|---|
| 运行时 | Python 3.9 | 与当前后端版本一致 |
| Web | FastAPI | 复用现有 API 模式 |

| ORM | SQLAlchemy 2 | 同步 Session |
| 数据库 | MySQL 8.0+ | 独立 `kiko_knowledge` 数据库 |
| 迁移 | Alembic | 表结构和索引版本 |
| 异步任务 | Celery 5 | 判断与恢复任务 |
| Broker | Redis | 独立队列和 key 前缀 |
| HTTP | requests | 当前生产依赖已存在 |
| 对象存储 | 阿里云 OSS SDK V2 | 教材媒体和导入原文件 |
| 模型调用 | OpenAI 兼容 HTTP JSON | 首期使用一个配置化模型 |

| 代码质量 | Ruff、pre-commit | 沿用当前门禁 |

### 5.1 明确不选

| 技术 | 首期不选原因 | 引入条件 |
|---|---|---|
| 微服务拆分 | 领域规模和团队尚不足 | 单服务部署或团队边界成为瓶颈 |
| 图数据库 | 目标关系量可由 MySQL 处理 | 多跳图查询成为已测瓶颈 |
| Kafka | 没有跨团队高吞吐事件流 | Celery 无法满足可靠任务需求 |
| Elasticsearch | 教材包过滤后的数据量较小 | MySQL/内存召回达不到指标 |
| 向量数据库 | 首期可由结构化召回和模型比较完成 | 黄金集 Top5 Recall 不达标 |
| Kubernetes 专属能力 | 与当前部署无关 | 统一基础设施要求 |

### 6.1 分层规则

依赖方向固定：

```text
app/main.py
  → app/api/v1/
    → app/domains/*/service.py
      → app/repositories/、app/providers/、app/models/
```

- Router 只处理 HTTP、依赖和响应；
- Service 负责业务规则、状态迁移和事务提交；
- Repository 负责查询和数据库锁，不提交事务；
- Provider 负责模型和对象存储；
- Worker 只调用 Runtime/Service；
- 不创建 BaseService、通用 Repository、DI 容器或一行转发类；
- 每个 Python 文件不超过 500 行。

## 8. 数据模型设计

### 8.1 总体策略

知识内容采用“完整版本快照”：

- 每个知识包发布版本拥有自己的课程节点、目标、关系和样题行；
- 创建新草稿时从指定发布版本克隆；
- 克隆保留 `logical_id`，生成新的数据库行ID；
- Published 版本不可修改；
- 内容量较小，优先用存储换取简单、可靠的历史追溯。

无需构建复杂的“稳定实体 + 多层 revision”模型。

### 8.2 ID与时间

- 数据库主键使用 26 位 ULID；
- `logical_id` 是跨版本稳定业务ID；
- 数据库存 UTC `DATETIME(3)`；
- API 使用 ISO 8601 UTC；
- 逻辑删除只用于尚未发布草稿；
- 已发布内容使用 `status=deprecated`，不物理删除。

约束：

- Service 校验两个目标属于同一版本；
- prerequisite_of 禁止形成环；
- split_from/merged_into 允许指向版本内 deprecated 目标。

##### 跨知识包等价映射

不同教材版本之间的等价目标不塞进版本内 relation 表，单独使用
`cross_package_objective_mappings`：

- source_package_version_id；
- source_objective_logical_id；
- target_package_version_id；
- target_objective_logical_id；
- mapping_type=equivalent/overlap；
- metadata_json；

## 9. 知识包版本与发布

### 9.1 状态机

```text
draft → in_review → published → deprecated
   ↑         │
   └─────────┘ rejected
```

### 9.2 创建新版本

在一个事务中：

1. 锁定 curriculum_packages；
2. 校验 based_on_version 是 Published；
3. 创建 Draft package_versions；
4. 批量克隆课程节点、目标、关系、样题、关联和外部映射；
5. 保留 logical_id，生成新行ID；
6. 重建版本内外键映射；
7. 提交。

知识包规模较小，首期允许同步克隆。实测超过接口超时后再迁移 Celery，不提前异步化。

### 9.3 提交审核

提交前执行：

- 必填字段；
- 目录无环；
- 目标属于有效课程节点；
- 前置关系无环；
- 目标发布最低样题要求；
- 正例、边界和反例关联合法；
- 外部映射无重复；
- 教材媒体授权完整；
- 任务特征 Schema 合法。

检查失败返回具体资源ID和错误码，版本保持 Draft。

### 9.4 发布事务

1. 锁定 package 和待发布 version；
2. 校验状态为 in_review；
3. 校验审核已通过；
4. 校验黄金集运行通过；
5. 将 version 标记 Published；
6. 更新 package.current_release_id；
7. 写 audit_log；
8. 提交。

Published 内容不得再 UPDATE 或 DELETE。

### 9.5 回滚

回滚只修改 package.current_release_id 指向历史 Published 版本并写审计。

不删除问题版本，不修改已完成判断冻结的知识包版本集合。

## 10. 题目判断架构

### 10.1 总体流程

```text
提交请求
  → 冻结知识包版本
  → 创建 classification_task
  → 投递 Celery
  → 规范化题目
  → 召回候选目标和样题
  → 模型在候选内比较
  → 程序校验目标、证据和授权
  → 程序计算范围状态
  → 校准置信度
  → 原子保存结果
  → 返回 completed / needs_review
```

### 10.2 创建任务事务

1. 鉴权 Client App；
2. 校验请求和媒体引用；
3. 根据请求版本或 latest_stable 解析 active Published 版本；
4. 解析调用方明确提供的 previous/later 知识包并冻结其 Published 版本；
5. 校验调用方对全部版本有访问权限；
6. 规范化文本并计算 SHA-256；
7. 以 `client_app_id + client_request_id` 查询幂等记录；
8. 不存在则创建 classification_task 和 classification_task_packages；
9. 提交后投递 Celery；
10. 返回 202。

消息投递失败时任务保留 received，由维护任务恢复。

### 10.3 Worker抢占

Worker 以 task_id 为唯一输入：

1. 对 task 行加锁；
2. completed/needs_review/failed 直接返回；
3. processing 且未超时直接返回；
4. received 或已超时 processing 更新为 processing；
5. 设置 processing_started_at；
6. 提交后执行外部模型调用。

模型调用期间不持有数据库事务和行锁。

### 10.4 题目规范化

规范化包括：

- Unicode NFKC；
- 全角空格和常见标点统一；
- 保留数学符号、题号结构和图片占位符；
- 合并题干、选项和调用方确认解析；
- 去除调用方 UI 文案；
- 限制总长度；
- 计算稳定 question_hash。

不在知识服务重复执行 OCR。媒体只作为可选补充。

### 10.5 媒体安全

P0 优先使用调用方提供的 OCR 和 structured_content。

如果提供 media_url：

- 仅允许 HTTPS；
- Host 必须在 Client App allowlist；
- 禁止重定向；
- 设置连接和读取超时；
- 限制响应大小和 MIME；
- 禁止访问内网、localhost 和云元数据地址；
- 失败时优先继续使用文本，并写 warning；
- 文本不足时返回 needs_review。

### 10.6 召回候选

候选池包含：

- 当前知识包版本；
- 调用方明确允许的前置和后续知识包版本；
- 状态为 active 的教学目标；
- 目标关联的 prototype、boundary 和 counterexample。

P0 召回步骤：

1. 按知识包和课程范围过滤；
2. 从 objective 定义、概念、操作和 match_hints 匹配；
3. 从 exemplar 题面、标准解法和 task_signature 匹配；
4. 使用字符 n-gram、关键词覆盖、字段精确匹配和反例冲突计算召回分；
5. 每个目标保留最强样题证据；
6. 返回 Top 10 目标给模型；
7. 保存 Top 5 为正式候选。

首期在过滤后的包内进行 O(n) 评分，不引入新检索服务。单次参与评分的 active exemplars 上限建议 5,000；超过或达不到 Top5 Recall 指标时再引入 MySQL FULLTEXT ngram 或向量索引。

### 10.7 模型比较

模型输入仅包含：

- 规范化题目；
- 调用方提供的结构化内容；
- Top 10 候选目标ID、定义、必要概念和必要操作；
- 每个候选少量已授权样题摘要；
- 候选边界和反例摘要；
- 允许返回的匹配类型枚举。

模型不得：

- 创建新的教学目标ID；
- 自由判断课程范围；
- 返回未经候选列表提供的样题；
- 修改标准答案；
- 输出内部思维过程；
- 将 unmatched 等同于 later_scope。

模型输出经过 Pydantic Schema 校验：

```json
{
  "primary_objective_id": "obj_x",
  "secondary_objective_ids": [],
  "match_type": "variant",
  "evidence_exemplar_ids": ["ex_x"],
  "task_signature": {
    "question_goal": "...",
    "required_method": ["..."],
    "required_concepts": ["..."],
    "input_form": ["..."],
    "output_form": ["..."],
    "difficulty_features": []
  },
  "reason_summary": "..."
}
```

### 10.8 程序校验

模型输出必须通过：

1. 主要目标在候选列表；
2. 次要目标在候选列表且不重复；
3. 目标属于 classification_task_packages 冻结版本集合；
4. evidence 样题存在；
5. evidence 与所选目标存在 primary/supporting 关联；
6. counterexample 不作为正向证据；
7. evidence 有权向当前调用方展示；
8. match_type 使用合法枚举；
9. reason_summary 长度和内容安全；
10. unmatched 不包含主要目标和 later_scope。

任何关键校验失败不写入成功结果。允许一次模型修复重试；仍失败转 needs_review。

### 10.9 范围计算

模型不计算 scope_status。

程序根据：

- active_package_id；
- active_node_ids；
- learned_through_node_id；
- 主要和次要目标的课程节点；
- package/node 顺序；
- prerequisite 和等价关系

计算：

| 条件 | 结果 |
|---|---|
| 没有 scope_context | unknown_scope |
| unmatched | unknown_scope |
| 所有主要目标在 active_node_ids | in_scope |
| 目标明确早于 learned_through_node_id | previous_scope |
| 目标明确晚于 learned_through_node_id | later_scope |
| 多个必要目标分布在范围内外 | cross_scope |
| 顺序或关系不足 | unknown_scope |

later_scope 只有在目标匹配达到高置信度且课程顺序明确时成立，否则降为 unknown_scope。

### 10.10 置信度

不直接把模型自报分数当概率。

P0 使用可解释信号：

- 召回 Top1 分；
- Top1/Top2 间隔；
- 模型选择是否与召回 Top1 一致；
- 是否存在强反例冲突；
- evidence 是否完整；
- OCR/结构化告警；
- 输出校验是否需要修复；
- 黄金集校准配置。

输出 `confidence_score` 仅表示经过当前 classifier_version 校准的判断强度。

默认门槛：

- ≥ 0.85：高，可自动推荐；
- 0.65–0.85：中，需要确认；
- < 0.65：低，needs_review 或 unmatched。

门槛配置跟随 classifier_version，不跟随客户端自由修改。

### 10.11 结果落库

在一个事务中：

1. 锁定 classification_task；
2. 重新确认仍为 processing；
3. 删除同任务未完成的临时候选；
4. 写入 candidates；
5. 写入 result 和 result_objectives；
6. 写入 evidence；
7. 将任务更新为 completed 或 needs_review；
8. 写 completed_at；
9. 提交。

历史结果不因知识包或模型升级被覆盖。重新判断创建新的 client_request_id。

### 10.12 Provider失败

- 网络超时、429、5xx：最多重试2次；
- 非法 JSON 或 Schema 失败：允许一次修复重试；
- 候选为空：直接 unmatched + unknown_scope；
- Provider 最终失败但有候选：needs_review，保留候选；
- Provider 最终失败且无候选：failed；
- 不用低质量规则结果冒充高置信度结果。

## 11. 判断任务状态与恢复

### 11.1 状态机

```text
received → processing → completed
                     ↘ needs_review
                     ↘ failed
```

终态不可重新打开。用户请求重试时创建新任务或由明确的 retry 接口将可恢复 failed 任务生成新任务。

### 11.2 恢复扫描

Celery Beat 定期扫描：

- received 且超过投递等待时间；
- processing 且超过处理超时；
- retry_count 未超过限制。

恢复时：

1. 锁定任务；
2. 增加 retry_count；
3. 重置为 received；
4. 提交；
5. 重新投递。

不得依赖 Celery Result Backend 恢复业务状态。

### 11.3 幂等

- 创建任务：`client_app_id + client_request_id` 唯一；
- Worker：task_id 幂等；
- 结果：task_id 唯一；
- 反馈：支持调用方 feedback_request_id 唯一；
- 发布：package_id + version 唯一；
- 导入：package_version_id + source_hash 唯一。

## 13. 鉴权与权限

### 13.1 Client App鉴权

P0 使用高熵 API Key，不建设 OAuth Server。

Token格式：

```text
kh_live_{key_id}.{32字节随机secret}
```

服务端：

1. 解析 key_id；
2. 查询 active client_app；
3. 使用服务端 pepper 计算 secret HMAC/SHA-256；
4. 使用 constant-time compare；
5. 校验过期时间、知识包权限和限流；
6. 日志只记录 key_id，不记录 secret。

### 13.2 管理端身份

P0 不自建用户名密码系统。

建议由公司 SSO 或身份代理完成登录，知识服务只接收可信 subject，并在本地映射角色。

要求：

- 管理 API 不直接暴露公网；
- 仅代理可写入身份 Header；
- 直连服务时忽略外部伪造 Header；
- development 可启用本地测试身份，非 development 启动时强制关闭。

### 13.3 RBAC

- Viewer：只读；
- Editor：修改 Draft；
- Reviewer：审核内容和反馈；
- Publisher：发布、回滚、弃用；
- Admin：身份、调用方和系统配置。

Service 层再次校验权限，不能只依赖前端隐藏按钮。

## 14. 当前产品接入

### 14.1 接入方式

当前后端新增：

```text
app/providers/knowledge_service.py
```

Provider 负责：

- 服务间 Bearer Token；
- 创建判断任务；
- 查询判断状态；
- 提交反馈；
- 超时和错误码转换；
- 不包含业务状态迁移。

领域 Service 负责：

- 创建本地 KnowledgeMatchTask；
- 保存 external_classification_id；
- 将远端结果转换为本地候选；
- 映射新 objective_id 到旧 knowledge_point_id；
- 驱动现有 Flow；
- 继续执行当前产品范围和生成权限判断。

### 14.2 当前表最小扩展

`knowledge_match_tasks` 建议新增：

- external_classification_id；
- knowledge_package_id；
- knowledge_package_version；
- classifier_version；
- external_primary_objective_id；
- match_type；
- curriculum_scope_status；
- evidence_json；
- remote_result_snapshot_json。

`knowledge_match_candidates` 建议新增：

- external_objective_id；
- matched_exemplar_ids_json；
- remote_score_details_json。

旧 `knowledge_point_id` 和 `confirmed_knowledge_point_id` 暂时保留，继续支持生成、错题和旧查询。

### 14.3 异步流程调整

现有题目确认后同步匹配，接入后改为：

```text
题目确认
  → 创建本地 match task
  → 调用知识服务创建 classification
  → 本地 Flow 保持 knowledge_matching
  → 当前后端 Celery 同步任务轮询远端状态
  → 保存远端结果和本地映射
  → Flow 进入 knowledge_confirm_pending
```

复用当前 Celery/Redis，不在 HTTP GET 中偷偷执行远端同步和状态迁移。

轮询任务使用 Celery retry/countdown，不使用阻塞 sleep。

### 14.4 无旧ID映射

如果知识服务返回的目标没有当前产品 external mapping：

- 仍可展示目标名称和教材依据；
- 本地候选不写伪造 knowledge_point_id；
- 标记 generation_supported=false；
- 用户可以完成题目归属确认；
- 变式题生成返回现有 `KNOWLEDGE_GENERATION_UNSUPPORTED`；
- 由教研或研发补充映射和生成模板。

### 14.5 当前范围映射

知识服务返回的 scope_status 不直接替换当前 `ScopeCheckRecord`。

当前产品按以下输入继续决定业务状态：

- 远端教学目标和课程位置；
- 当前孩子学习进度快照；
- 前置满足率；
- 当前掌握反馈；
- 当前产品生成策略。

远端范围结论保存为证据字段，最终 `normal/slightly_ahead/out_of_scope/uncertain` 仍由当前产品产生。

### 14.6 故障降级

知识服务失败时：

- 本地 match task 标记 remote_unavailable；
- Flow 回到 knowledge_confirm_pending；
- 用户可稍后重试或人工选择；
- 影子阶段可继续使用旧匹配器；
- 正式切换后不得静默用旧规则冒充新服务结果；
- 不影响题目文本和 OCR 结果保存。

## 15. 数据迁移

### 15.1 迁移原则

- 不直接移动生产表；
- 通过导出、导入和 external mapping 建立新知识包；
- 当前后端课程表继续只读兼容；
- 新服务验证完成前不改变现有业务事实；
- 迁移脚本可重复运行。

### 15.2 首版知识包生成

导出当前：

- curriculum_versions；
- curriculum_chapters；
- knowledge_points；
- knowledge_point_prerequisites；
- knowledge_point_keywords。

转换为：

- curriculum_packages；
- package_versions；
- curriculum_nodes；
- objectives；
- objective_relations；
- objective_external_mappings。

`question_templates` 不导入知识服务，只可作为教研补充标准解法时的参考输入。

### 15.3 样题建设

现有生成模板不能自动等同于教材样题。

样题必须来自：

- 获授权教材；
- 配套练习；
- 教研确认题；
- 审核通过的线上反馈。

导入时记录来源、页码、题号和授权。

### 15.4 双跑

影子阶段保存：

- 旧 Top3 和最终选择；
- 新 Top5、最终目标、类型、范围和证据；
- 用户最终修正；
- 知识包和模型版本。

对比报告按目标、题型和范围状态输出，不只看总准确率。

### 15.5 切换

满足上线门槛后：

1. 新服务驱动候选；
2. 旧匹配器保留只读回退开关；
3. 稳定后关闭自动回退；
4. 旧知识点停止新增；
5. 后续是否删除旧匹配代码另行评审。

## 16. 事务与一致性

### 16.1 不使用分布式事务

当前后端和知识服务之间使用：

- 调用方幂等键；
- 远端 classification_id；
- 本地结果快照；
- 可重试查询；
- 最终一致性。

知识服务成功而当前后端写入失败时，当前后端重试查询同一 classification_id。

### 16.2 关键事务

| 事务 | 必须原子完成 |
|---|---|
| 创建判断任务 | 冻结版本、写任务、写幂等键 |
| Worker抢占 | 校验状态、更新 processing |
| 保存判断结果 | 候选、结果、证据、任务终态 |
| 发布 | 版本状态、current_release_id、审计 |
| 回滚 | current_release_id、审计 |
| 提交反馈 | 反馈记录、幂等键 |
| 审核反馈 | 审核结果、候选动作、审计 |

外部模型、OSS 和 HTTP 调用不得在数据库事务内执行。

### 16.3 并发编辑

Draft 资源使用 `updated_at` 或 `lock_version` 做乐观锁：

- 管理端提交携带版本；
- 版本不一致返回 409；
- 不静默覆盖其他编辑者内容。

P0 使用每行整数 `lock_version`，不引入协同编辑。

## 17. 导入与导出

### 17.1 导入文件

JSON/CSV上传后：

1. 校验文件类型、大小和编码；
2. 计算 SHA-256；
3. 保存私有 OSS；
4. 创建 import job；
5. 解析为临时结果；
6. 返回错误行和预览；
7. 用户确认后在一个事务写入 Draft；
8. 保存导入审计。

P0 数据量可在 API 内解析和预览；实际写入量超过接口限制后再改为 Celery。

### 17.2 幂等

同一 package_version_id + source_hash 重复导入返回原 import job。

### 17.3 导出

Published 知识包支持导出为版本化 JSON，内容包括：

- 目录；
- 目标；
- 关系；
- 样题元数据；
- 外部映射；
- 内容哈希。

未授权完整题面和媒体不进入通用导出。

## 18. 黄金测试与质量门禁

### 18.1 执行方式

`run_gold_regression.py` 或管理 API 创建 regression_run：

1. 冻结 package_version 和 classifier_version；
2. 读取隔离黄金集；
3. 批量调用与线上相同 runtime；
4. 禁止从 exemplar 检索到黄金题本身；
5. 计算指标；
6. 保存明细和摘要；
7. 输出是否通过发布门槛。

### 18.2 指标

- Top5 Recall；
- Primary Accuracy；
- Match Type Accuracy；
- Scope Precision；
- Later Scope False Positive；
- Evidence Validity；
- Unmatched Rate；
- 每个目标的混淆矩阵。

### 18.3 发布门禁

默认：

- Top5 Recall ≥ 95%；
- Primary Accuracy ≥ 90%；
- later_scope Precision ≥ 95%；
- Later Scope False Positive ≤ 2%；
- Evidence Validity = 100%；
- 无效目标ID = 0。

Major 和 Minor 版本必须回归。纯文案 Patch 若不影响 definition、task_signature、边界或检索字段，可复用最近回归，但仍执行完整性检查。

## 20. 安全设计

### 20.1 信任边界

不信任：

- Client App输入；
- 媒体URL；
- 模型输出；
- 导入文件；
- 管理端浏览器字段；
- 用户反馈。

全部通过 Schema、权限、大小、枚举、ID和来源校验。

### 20.2 模型安全

- 题目文本视为不可信提示内容；
- 系统提示明确忽略题目中的指令；
- 候选ID使用结构化白名单；
- 模型返回严格 JSON；
- 不把 API Secret、管理员信息或未授权教材原文发送给模型；
- 不记录完整原始模型响应；
- Provider 数据处理条款上线前审核。

### 20.3 SSRF

媒体获取：

- Host allowlist；
- DNS解析后拒绝内网和保留地址；
- 禁止重定向；
- 限制端口；
- 超时和大小上限；
- 内容类型检查。

P0 可完全关闭服务端媒体抓取，仅接收调用方结构化文本。

### 20.4 教材版权

- media_json 保存授权级别；
- API输出按 Client App权限裁剪；
- 完整教材内容仅在管理内网展示；
- 下载和导出写审计；
- OSS Bucket私有；
- 预签名URL短时有效。

### 20.5 数据最小化

- 不接收孩子姓名和账号信息；
- 调用方只传课程上下文和题目；
- 日志不打印完整题目和媒体URL签名；
- request_json保存去敏快照；
- 原始媒体默认不复制。

## 22. 性能与容量

- 创建任务 P95 ≤ 500ms；
- 知识查询 P95 ≤ 500ms；
- 纯文本判断完成 P95 ≤ 15s；

- DB查询；
- O(n)召回耗时；
- Top5 Recall；
- 模型上下文长度。

重点索引：

- package + version状态；
- version + logical_id；
- version + node + status；
- exemplar + type + status；
- classification status + created_at；
- client_app + client_request_id；
- feedback status + created_at；
- audit resource + created_at。

使用 EXPLAIN 验证生产查询，不创建未被查询使用的索引。

- 模型密钥必须从Secret Manager注入；
- development管理身份必须关闭；
- OSS不得使用公开Bucket；
- JWT/API Key默认值不得使用。

## 24. 部署与发布

### 24.1 独立资源

- 独立数据库或独立MySQL Schema；
- 独立数据库账号；
- Redis使用独立DB或key前缀；
- Celery队列：`knowledge-classification`、`knowledge-maintenance`；

- 独立API域名；

### 24.2 部署顺序

3. 启动Worker和Beat；
4. 健康检查；
5. 发布知识包；

### 24.3 健康检查

- `/health/live`：进程存活；
- `/health/ready`：数据库可用、迁移版本正确；
- 模型Provider和Redis不阻断ready，但单独暴露依赖状态。

### 24.4 回滚

- 回滚镜像；
- 数据库Migration必须向前兼容前一版本；
- 破坏性字段删除至少跨两个版本。

知识包回滚：

- 修改current_release_id；
- 不回滚应用；
- 不删除判断历史。

## 26. 技术验收标准

### 26.1 架构

- 新服务独立部署和独立数据库；
- 当前产品只通过API调用；
- 没有跨库外键；
- 没有分布式事务；
- 没有引入图数据库、Kafka或新检索平台；
- 第二套教材接入不修改核心代码和表结构。

### 26.2 数据

- Published版本不可变；
- logical_id跨版本稳定；
- 任意判断可追溯知识包和模型版本；
- 拆分、合并和弃用不删除历史；
- 外部ID映射支持当前产品。

### 26.3 判断

- 模型只能从候选ID选择；
- scope由程序计算；
- unmatched不产生later_scope；
- counterexample不能作为正向证据；
- evidence展示受版权权限控制；
- 低置信度不自动确认。

### 26.4 可靠性

- 创建、Worker和反馈均幂等；
- Worker丢失可恢复；
- Provider失败不伪造结果；
- 当前产品可在知识服务失败时继续保存题目；
- 发布和应用均可回滚。

### 26.5 工程质量

- Ruff通过；
- pytest通过；
- 覆盖率≥80%；
- 文件≤500行；
- OpenAPI契约测试通过；
- MySQL集成测试通过；
- 黄金集门禁通过。

## 27. 主要风险

| 风险 | 技术影响 | 处理 |
|---|---|---|
| 教材数据不足 | 候选召回不稳定 | 补样题、边界和反例，不先堆模型 |
| 模型选择漂移 | 同题结果变化 | 冻结模型、prompt和知识包版本 |
| 当前产品生成强依赖旧ID | 新目标无法生成 | external mapping和本地兼容投影 |
| 范围职责重复 | 两套结论冲突 | 服务只给课程范围，产品决定业务权限 |
| 发布内容误改 | 历史不可追溯 | 完整版本快照和不可变Published |
| 媒体URL导致SSRF | 安全事件 | P0关闭或严格allowlist |
| 教材版权泄露 | 合规风险 | 最小返回、授权字段、私有OSS、审计 |
| O(n)召回变慢 | 判断延迟增加 | 达到实测阈值后升级检索 |
| 双跑期逻辑复杂 | 当前流程回归 | Provider隔离、任务快照和契约测试 |

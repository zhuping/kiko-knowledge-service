## 1. 文档说明

### 1.1 目标

本文档用于指导“乐学知低年级教育辅助 App——知识体系平台”V1.0 后端实现。方案以以下资料为业务输入：

- 《01-一年级数学原子知识点.md》
- 《02-二年级数学原子知识点.md》
- 《01-知识体系平台产品需求文档（PRD）.md》
- 《知识体系平台接口契约文档.md》

PRD 中的接口设计仅作为业务场景参考；接口路径、字段、发布模型和错误处理以本文档为准。
接口契约文档是前后端联调时的字段、枚举、错误码和任务结构唯一依据。

### 1.2 V1 范围

- 支持人教版小学数学 2024 审定新版（六三制）一年级、二年级上下册。
- 支持五级知识结构：领域、主题、单元、知识点组、原子知识点。
- 支持知识对象、教材目录、教材映射、政策规则映射、知识关联、草稿、发布、版本预览和回滚。
- 支持内部运营后台接口，以及面向业务端的已发布内容只读接口。
- 支持 Markdown/Excel 初始数据导入，Excel 批量导入和错误报告。

### 1.3 V1 不做

- 不做题库、OCR 识别、题目最终知识点匹配和学生掌握度计算。
- 不做 C 端用户、学习记录、推荐算法和复杂知识图谱可视化编辑。
- 不强制微服务、分库分表、读写分离、搜索引擎或消息队列。
- 不把 `supplement`、`activity` 或“未掌握”直接当作永久超纲结论。

## 2. 关键技术决策

| 项目 | 决策 |
| --- | --- |
| 服务形态 | Python 模块化单体；后台写接口和开放只读接口同仓库、分路由、分权限 |
| Web 框架 | FastAPI |
| Python | Python 3.9 |
| ORM/数据库访问 | SQLAlchemy 2.x 风格 + Alembic |
| MySQL 驱动 | PyMySQL；使用 SQLAlchemy 连接池 |
| 数据库 | MySQL 8，InnoDB，`utf8mb4` |
| 数据校验 | Pydantic 请求/响应模型 + 领域服务校验 |
| Excel | openpyxl，仅用于导入、导出和模板生成 |
| 任务执行 | MySQL 任务表 + 独立 worker；V1 不引入 Celery/Redis |
| 管理端鉴权 | 优先接入现有 SSO/OIDC；后端只负责令牌校验和角色映射 |
| 业务端鉴权 | AppKey + HMAC-SHA256，Secret 只在服务端保存 |
| 部署 | HTTPS 网关/Nginx → FastAPI；MySQL 独立部署 |

### 2.1 为什么采用模块化单体

V1 的主要压力是内容维护、校验和版本发布，数据量有限且业务边界集中。模块化单体可以保留清晰的领域边界，同时减少服务发现、分布式事务、消息一致性和部署运维成本。等题库同步或高并发查询成为独立负载后，再拆分开放查询服务。

### 2.2 数据源的边界

原子知识点文档中的以下字段进入后端领域模型：

- `canonical_id`
- `type`
- `name`
- `pep24_path`
- `ocr_signals`
- `exercise_signature`
- `prerequisites`
- `scope`

其中 `canonical_id` 是跨教材稳定 ID，创建后不可修改、不可复用。`pep24_path` 和教材相关字段落在教材映射/目录模型中，`ocr_signals` 拆成可检索词项；教材版本、册次、单元、小节、页码和映射类型不写入 `canonical_id`。

以下内容不创建新的原子知识对象：

- `review_set`：使用集合或映射维护。
- 生活场景：使用场景标签维护。
- 进位、退位、凑十、破十等：使用策略对象或方法标签维护。
- 易错点：使用易错标签维护。
- 题目难度、数值大小、未知量位置：由题库或业务端维护。

## 3. 总体架构

```text
运营后台 / 业务 App
          │ HTTPS + JSON
          ▼
网关/Nginx
  ├─ TLS 终止
  ├─ IP/调用方限流
  └─ 请求大小限制
          ▼
FastAPI 模块化单体
  ├─ admin API：草稿、导入、映射、关系、发布、审计
  ├─ open API：已发布知识查询
  ├─ domain service：规则校验、快照构建、回滚
  └─ worker：导入、导出、发布校验等任务
          │
          ├──────── MySQL 8：草稿、版本快照、审计、任务
          └──────── 文件临时目录/对象存储：导入文件和导出文件
```

### 3.1 读写边界

- 后台接口读写当前编辑空间，不直接修改正式快照。
- 开放接口只读正式快照，不读取草稿表。
- 发布通过一次数据库事务生成新的正式版本，并原子更新当前版本指针。
- 业务端按 `releaseVersion` 缓存数据；不设计“主动同步所有业务端缓存”的强耦合调用。

### 3.2 统一约束

- 内部字段使用 `snake_case`，API 字段使用 `camelCase`。
- API 长期引用只使用 `canonicalId`，不使用 `knowledgeCode`、教材路径或展示名称。
- 所有时间使用 UTC 存储，接口统一返回 ISO 8601 时间。
- 所有写操作带乐观锁版本号，避免运营人员互相覆盖内容。
- 正式版本只追加、不更新、不删除。

## 4. 领域模型

### 4.1 核心对象关系

```text
教材版本 1 ─── N 目录节点（领域/主题/单元/知识点组）
                         │
                         └── N 原子知识点挂载

知识对象 1 ─── N 教材映射 ─── 目录节点/教材路径
知识对象 1 ─── N 政策规则映射 ─── 政策规则版本
知识对象 N ─── N 知识对象关系

当前编辑空间 ──发布批次──> 正式版本快照
正式版本快照 ────────────> 开放只读接口
```

### 4.2 五级树的落地方式

- 1～4 级使用 `catalog_node`，通过 `parent_node_id` 建立父子关系。
- 5 级使用 `catalog_knowledge_node`，通过 `parent_group_node_id` 挂载到四级知识点组。
- 五级节点关联 `knowledge_object`，因此同一个知识对象可以在不同教材位置复用。
- 数据库保留父子关系，层级是否合法由领域服务校验；MySQL 外键无法单独表达“父节点必须是上一级”。

树接口必须把 `catalog_node` 和 `catalog_knowledge_node` 归一化为同一种树节点 DTO。第五级节点至少返回 `id`、`key`、`level=5`、`nodeType=knowledge`、`canonicalId`、`title`、`status` 和空 `children`，前端不直接感知两张表的差异。

第五级原子知识点的新增、挂载、移动和排序使用独立接口：

- 新增知识对象时必须同时传入 `groupNodeId`，或先创建知识对象再调用挂载接口。
- 目录节点移动只处理 1～4 级；第五级节点移动只允许在同一四级知识点组内排序。
- 第五级节点停用和知识对象停用分别记录变更；正式版本引用过的对象不硬删除。

V1 API 将 1～5 级统一返回为知识树节点 DTO。新增知识对象必须携带 `groupNodeId`，由后端在同一事务中创建知识对象和五级挂载关系；五级节点移动/排序调用独立的 `catalog-knowledge-nodes/{id}/move` 接口。前端不直接操作 `catalog_knowledge_node` 表。

### 4.3 关系模型

数据库只保存一种必要方向：

- `prerequisite`：`from_knowledge_id` 是 `to_knowledge_id` 的前置。
- `parallel`：同类并列关系，保存一条规范化记录，查询时按两端返回。
- `cross`：跨主题关系，保存一条带说明的记录，查询时按两端返回。

API 返回 `prerequisites`、`successors`、`parallel`、`cross` 四组数据。`successors` 由 `prerequisite` 的反向边计算，不单独保存，避免双写不一致。

## 5. 数据库设计

### 5.1 通用约定

- 引擎：InnoDB。
- 字符集：`utf8mb4`，排序规则使用项目统一的 `utf8mb4` 排序规则。
- 主键：内部表使用自增 `BIGINT UNSIGNED`；外部请求 ID 使用 UUID 字符串。
- 时间：`DATETIME(3)`。
- 删除：正式引用过的内容不物理删除，使用状态字段或删除标记。
- 所有业务表包含 `created_at`、`updated_at`；可追溯表额外包含操作者。

### 5.2 业务基础表

#### `content_space`

编辑空间。V1 默认只有一个 `default` 空间，但保留空间 ID 以支持后续草稿分支。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `space_code` | VARCHAR(64) | 唯一编码，如 `default` |
| `name` | VARCHAR(100) | 空间名称 |
| `status` | VARCHAR(20) | `active/inactive` |

#### `textbook_edition`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `edition_code` | VARCHAR(64) | 唯一编码，如 `pep_math_2024_63` |
| `edition_name` | VARCHAR(200) | 教材版本名称 |
| `subject` | VARCHAR(50) | 学科，V1 为数学 |
| `school_system` | VARCHAR(20) | V1 为六三制 |
| `version_year` | SMALLINT | 版本年份 |
| `status` | VARCHAR(20) | `active/inactive` |

#### `knowledge_object`

稳定的通用知识对象。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 内部主键 |
| `canonical_id` | VARCHAR(128) | 全局唯一、创建后不可修改 |
| `name` | VARCHAR(100) | 标准名称 |
| `type` | VARCHAR(32) | `concept/skill/problem_model/strategy/activity` |
| `grade_term` | VARCHAR(32) | 一年级/二年级上下册 |
| `scope` | VARCHAR(20) | `core/supplement` |
| `cognitive_level` | VARCHAR(20) | `remember/understand/apply/analyze`，前端显示为识记/理解/应用/分析 |
| `importance` | VARCHAR(20) | `core/important/general`，前端显示为核心/重要/一般 |
| `exercise_signature` | TEXT | 题型结构摘要，不存教材题目原文 |
| `solution_feature` | VARCHAR(1000) | 解题思路特征 |
| `scene_feature` | VARCHAR(1000) | 场景结构特征 |
| `numeric_feature` | VARCHAR(500) | 数值特征 |
| `status` | VARCHAR(20) | `draft/active/disabled` |
| `row_version` | INT | 乐观锁版本 |
| `created_by` / `updated_by` | BIGINT | 操作者 |

`canonical_id` 建立唯一索引。建议使用正则校验：`^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$`。停用后的 ID 进入保留集合，不能重新分配。

API 层统一使用以下字段映射和枚举，不把数据库值直接暴露给前端：

| 业务字段 | API 字段 | API 取值 |
| --- | --- | --- |
| 知识点名称 | `knowledgeName` | 字符串 |
| 类型 | `knowledgeType` | `concept/skill/problem_model/strategy/activity` |
| 年级学期 | `gradeTerm` | `一年级上册/一年级下册/二年级上册/二年级下册` |
| 范围 | `scope` | `core/supplement` |
| 状态 | `status` | `draft/active/disabled` |
| 重要程度 | `importance` | `core/important/general` |
| 认知层级 | `cognitiveLevel` | `remember/understand/apply/analyze` |

前端展示中文文案，但请求和响应只使用上述稳定枚举；`knowledge_term` 映射为 `aliases`、`coreKeywords`、`derivativeKeywords` 和 `ocrSignals` 四组数组。

#### `knowledge_term`

用于检索的别名和关键词，不使用逗号拼接字符串。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `knowledge_id` | BIGINT | 知识对象 |
| `term_type` | VARCHAR(20) | `alias/core_keyword/derivative_keyword/ocr_signal` |
| `term` | VARCHAR(200) | 单条词项 |
| `sort_order` | INT | 排序 |

唯一索引：`(knowledge_id, term_type, term)`；检索索引：`(term, term_type, knowledge_id)`。

### 5.5 发布和审计表

#### `release_current`

当前正式版本指针表，固定只有一行：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TINYINT | 固定为 1 |
| `release_id` | BIGINT | 当前正式版本 |
| `updated_at` | DATETIME(3) | 指针更新时间 |

发布事务使用 `SELECT ... FOR UPDATE` 锁定该行，开放接口先读取指针再查询对应快照。

#### 发布快照表

正式内容使用与草稿分开的快照表，至少包括：

- `release_catalog_node`
- `release_catalog_knowledge_node`
- `release_knowledge_object`
- `release_knowledge_term`
- `release_textbook_mapping`
- `release_knowledge_relation`
- `release_policy_rule`
- `release_policy_mapping`

快照表均带 `release_id`，主键或唯一索引包含 `release_id`。开放接口绝不通过草稿表拼装数据。

### 5.6 任务、调用方和审计表

#### `job`

用于批量导入、导出和发布校验。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `job_type` | VARCHAR(30) | `import/export/validate/release` |
| `status` | VARCHAR(20) | `queued/running/success/failed/cancelled` |
| `total_count` | INT | 总量 |
| `success_count` / `failure_count` | INT | 处理结果 |
| `payload_json` | JSON | 参数 |
| `error_file` | VARCHAR(500) NULL | 错误报告地址 |
| `last_error` | VARCHAR(1000) NULL | 最后错误 |
| `created_by` | BIGINT | 操作者 |

#### `api_client`

保存开放接口调用方。

- `app_key` 唯一。
- `secret_ciphertext` 保存加密后的 Secret；解密密钥来自部署密钥管理，不写入代码和日志。
- `allowed_scopes` 保存接口权限。
- `status`、`rate_limit_per_minute`、`last_rotated_at` 用于调用方管理。

#### `api_nonce`

保存时间窗口内的 `(app_key, nonce)` 唯一记录，防止 HMAC 重放。定时清理过期记录。

#### `api_rate_bucket`

当网关不提供限流时的 MySQL 兜底计数器，按 `(app_key, bucket_minute)` 唯一；使用原子 `INSERT ... ON DUPLICATE KEY UPDATE` 累加请求数。该方案只覆盖 V1 的低并发内部调用，高并发时迁移到网关或 Redis。

#### `audit_log`

记录登录、导入、导出、编辑、映射、关系、停用、发布、回滚等操作，包含操作者、对象、摘要、结果、requestId。禁止保存 Secret、完整签名和敏感请求体。

## 7. 核心业务流程

### 7.1 保存草稿

1. 鉴权并校验角色。
2. 校验请求字段、枚举、ID 格式和父子节点层级。
3. 使用 `row_version` 做乐观锁更新。
4. 同一事务写入业务表、词项/关系表和 `change_log`。
5. 写入 `audit_log`，返回最新 `rowVersion`。

编辑者可以保存草稿；发布者和管理员也可以编辑，但是否允许发布由发布权限决定。

### 7.2 Excel 批量导入

```text
上传文件
  → 文件大小/扩展名/表头校验
  → 逐行解析
  → 业务预校验（不写业务表）
  → 返回行号、字段、原因、修复建议
  → 确认提交
  → 单事务写入当前编辑空间
  → 生成 change_log 和 audit_log
```

约束：

- 单次最多 1000 行。
- 预校验不改变数据库。
- 确认提交时要检查文件摘要和草稿空间版本，避免重复提交。
- 不允许部分成功；失败则整批回滚。
- 已存在 `canonical_id` 时只允许按明确的更新模式修改，不允许静默覆盖。
- Excel 是运营导入格式，源文档不作为运行时依赖。

导入主工作表固定为 `knowledge_points`，表头固定为：

```text
canonical_id,type,name,grade_term,scope,pep24_path,ocr_signals,exercise_signature,prerequisites
```

其中 `ocr_signals` 和 `prerequisites` 使用 JSON 数组字符串，例如 `[]` 或 `["m.num.recognize.1_5"]`；不接受逗号拼接数组。可选的 `prerequisites` 工作表仅用于关系明细展示，主导入结果以 `knowledge_points` 为准。

### 7.3 发布校验

发布批次选定一组 `change_log` 后，系统以“上一正式版本 + 本批次草稿变更”构建候选快照，再对候选快照校验。这样未选入本批次的其他草稿不会被发布。

校验规则：

1. **结构**：目录只能是 1→2→3→4；五级知识点只能挂到四级知识点组。
2. **字段**：必填字段完整，枚举值合法，`canonical_id` 格式正确且全局唯一。
3. **引用**：关系、教材映射、政策映射引用的对象存在。
4. **教材映射**：启用知识对象至少有一条有效教材映射；同知识对象、同教材位置、同映射类型不得重复。
5. **关系**：禁止自关联；前置关系无环；跨年级/跨学期关系必须有依据；平行关系按约定范围维护。
6. **快照一致性**：批次选择时的 `after_hash` 与当前草稿摘要一致。
7. **影响分析**：变更已被业务引用时展示影响范围，但不因引用而禁止正常回滚。

错误和风险分开：错误阻止发布；风险允许发布但必须由发布者确认。

### 7.4 正式发布

1. 锁定 `release_current` 当前版本指针。
2. 校验批次仍为 `passed`，且草稿摘要未变化。
3. 在同一事务中复制基础快照，并应用批次变更。
4. 对新快照计算 `content_hash`。
5. 写入新的 `release_version` 和全部 `release_*` 快照表。
6. 更新 `release_current`。
7. 更新批次、变更状态和审计记录。
8. 提交事务后，开放接口立即看到新版本；失败则整体回滚。

发布版本是不可变的。业务端通过 `releaseVersion` 或 `ETag` 缓存，不依赖后台逐个通知业务端。

### 7.5 回滚

回滚不是修改旧版本，而是以旧版本快照为来源创建新的 `rollback` 发布批次：

```text
选择历史正式版本
  → 生成差异和影响分析
  → 发布者确认
  → 复制历史快照为新版本
  → 新版本成为 current
```

中间版本保留，审计链包含原版本、回滚来源、操作人、原因和新版本。

### 7.6 任务执行

worker 使用 MySQL 8 的行锁领取任务：

```sql
SELECT id
FROM job
WHERE status = 'queued'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

领取后将状态改为 `running`，处理成功或失败后更新进度。任务处理器必须具备幂等性，重复执行不会产生重复映射、重复版本或重复审计结果。

任务查询统一返回：

```json
{
  "jobId": 1001,
  "jobType": "import",
  "status": "running",
  "totalCount": 1000,
  "successCount": 800,
  "failureCount": 10,
  "progressPercent": 81,
  "errorFileId": null,
  "canRetry": false
}
```

任务失败明细通过 `errorFileId` 下载，或在数据量较小时直接返回 `errors` 数组；重试必须调用后端任务重试接口，前端不重复上传或重复提交原任务。

导出统一使用：

```text
POST /api/v1/admin/exports
GET  /api/v1/admin/files/{fileId}
```

导出文件必须带教材版本、编辑空间或正式 `releaseVersion`，并使用短期有效的下载权限。

### 8.4.1 API 字段和枚举契约

数据库字段不直接暴露给前端，API 统一使用 camelCase。知识对象详情固定返回以下字段：

```json
{
  "canonicalId": "m.num.count.1_100",
  "knowledgeName": "100以内数数",
  "knowledgeType": "skill",
  "gradeTerm": "一年级下册",
  "scope": "core",
  "cognitiveLevel": "understand",
  "importance": "core",
  "status": "active",
  "aliases": [],
  "coreKeywords": [],
  "derivativeKeywords": [],
  "ocrSignals": [],
  "exerciseSignature": "按顺序数数、接着数",
  "solutionFeature": "",
  "sceneFeature": "",
  "numericFeature": "",
  "rowVersion": 1,
  "textbookMappings": []

```

固定枚举：

- `knowledgeType`：`concept`、`skill`、`problem_model`、`strategy`、`activity`。
- `scope`：`core`、`supplement`。
- `status`：`draft`、`active`、`disabled`。
- `cognitiveLevel`：`remember`、`understand`、`apply`、`analyze`。
- `importance`：`core`、`important`、`general`。

界面显示中文标签，提交和返回使用上述稳定枚举值。`knowledge_term.term_type` 映射为 `aliases`、`coreKeywords`、`derivativeKeywords`、`ocrSignals`；教材映射统一使用 `textbookPath`，人教版的 `pep24_path` 仅作为导入字段和业务别名。

### 8.5 管理端鉴权

管理端使用公司 SSO/OIDC 或受控会话 Cookie，不使用 AppKey + HMAC。后端提供：

```text
GET /api/v1/admin/me
```

返回当前用户的 `userId`、`displayName`、角色列表和权限列表。前端据此进行路由和按钮展示，后端仍对每个写接口执行最终权限校验。

### 8.6 开放接口鉴权

请求头：

```text
X-App-Key: app_xxx
X-Timestamp: 1780000000
X-Nonce: random-string
X-Signature: base64(hmac_sha256(secret, canonical_request))
```

签名原文固定为：

```text
HTTP_METHOD\n
REQUEST_PATH\n
SHA256(QUERY_STRING)\n
SHA256(REQUEST_BODY)\n
TIMESTAMP\n
NONCE
```

服务端按以下顺序处理：

1. 校验请求时间窗口，默认 ±300 秒。
2. 校验 AppKey 状态和接口权限。
3. 使用数据库唯一约束写入 `(appKey, nonce)`，重复即拒绝。
4. 计算签名并使用常量时间比较。
5. 再执行参数校验和业务查询。

V1 限流优先由网关按 AppKey 执行；没有网关时使用 MySQL 分钟桶作为后端兜底。若后续多实例高并发成为瓶颈，再替换为 Redis，不改变接口协议。

### 8.7 范围判断接口边界

`/scope:check` 只返回依据，不实现 OCR 或最终题目判断。输入可以包含：

```json
{
  "canonicalIds": ["m.op.add.within_5"],
  "editionCode": "pep_math_2024_63",
  "gradeTerm": "一年级上册",
  "ruleVersion": "2026.01",
  "questionContext": {}
}
```

返回应包含：

- `curriculumStatus`：课内、补充、未映射等。
- `complianceStatus`：通过、需人工确认、无依据。
- `reasons`：教材映射、适用年级、规则版本、关联依据。
- `releaseVersion`：使用的正式内容版本。

如果未提供已匹配的 `canonicalIds`，返回 `unmatched` 原因，由业务端先完成题目解析和候选匹配。

### 8.8 错误码

| HTTP | `code` | 说明 |
| --- | --- | --- |
| 400 | `PARAM_INVALID` | 参数格式或取值错误 |
| 401 | `AUTH_FAILED` | 未通过鉴权或签名校验 |
| 403 | `FORBIDDEN` | 角色或 AppKey 无权限 |
| 404 | `NOT_FOUND` | 资源不存在 |
| 409 | `CONFLICT` | 乐观锁、版本、重复数据冲突 |
| 422 | `VALIDATION_FAILED` | 发布或业务规则校验失败 |
| 429 | `RATE_LIMITED` | 超出调用频率 |
| 500 | `INTERNAL_ERROR` | 未预期服务异常 |
| 503 | `SERVICE_UNAVAILABLE` | 服务未就绪或任务不可用 |

批量操作错误必须返回行号/对象 ID、字段、原因和修复建议；响应和日志中不得出现 Secret、完整签名或敏感请求参数。

## 9. 权限设计

V1 只保留三种角色：

| 角色 | 草稿编辑 | 导入/导出 | 创建批次 | 执行校验 | 发布 | 回滚 | 停用/版本管理 |
| --- | --- | --- | --- | --- | --- | --- | --- |

## 10. 安全、稳定性和运维

### 10.1 安全

- TLS 在网关终止，内网服务间仍使用受控网络和最小权限账号。
- SQLAlchemy 参数化查询，禁止字符串拼接 SQL。
- 上传文件限制扩展名、MIME、大小和行数，文件存储使用随机文件名。
- 导出文件使用短期下载地址，过期自动清理。
- 管理端操作全量审计，关键操作二次确认。
- 数据库账号按读写、迁移、只读接口拆分权限。
- Secret 使用 KMS/部署密钥加密存储，绝不写入日志。

### 10.2 稳定性

- 健康检查：`/healthz` 只检查进程，`/readyz` 检查 MySQL 连接和迁移状态。
- 发布、回滚和批量导入使用事务；失败整批回滚。
- worker 任务支持失败重试和人工重试，超过次数进入 `failed`。
- 数据库每日备份，至少保留一份异地或独立存储备份；具体周期服从公司备份策略。
- 开放查询默认读取正式快照，避免草稿锁影响业务端。

### 10.3 日志和监控

结构化日志至少包含：`requestId`、接口、耗时、HTTP 状态、业务码、AppKey、操作者、releaseVersion。

监控指标：

- API QPS、P50/P95/P99 延迟、5xx、429、鉴权失败。
- MySQL 连接池使用率、慢查询、锁等待。
- 导入/校验/发布任务成功率和耗时。
- 当前正式版本、版本发布失败次数。

## 11. 性能和容量基线

V1 不预设不必要的分布式组件，先用 MySQL 索引和正式快照满足当前规模。建议验收基线：

- 常规树查询、详情查询：P95 ≤ 500ms。
- 条件检索：P95 ≤ 800ms。
- 批量详情不超过 100 个 `canonicalId`。
- Excel 单批不超过 1000 行。
- 发布校验单批不超过 5000 个变更对象。
- 开放接口错误率 ≤ 0.1%，具体并发数由压测结果校准。

搜索先使用 `knowledge_term` + MySQL 索引；V1 不引入 Elasticsearch。只有中文模糊检索、数据量或排序质量成为实际瓶颈时才升级搜索方案。

## 12. 初始数据导入方案

### 12.1 Markdown 到数据库

提供一次性脚本 `scripts/import_knowledge_markdown.py`：

1. 解析一级/二级标题得到学段和教材章节上下文。
2. 解析 Markdown 表格字段。
3. 按 `canonical_id` 去重；一年级和二年级文件重复 ID 复用同一个知识对象。
4. 将 `pep24_path` 按 `/` 创建教材目录节点和五级挂载节点。
5. 将 `prerequisites` 转换为 `knowledge_relation` 的 `prerequisite` 关系。
6. 将 `ocr_signals` 拆成 `knowledge_term`，不保留逗号拼接字段。
7. 执行完整预校验，输出缺失映射、未知前置 ID、重复 ID 和路径冲突。
8. 预校验通过后写入默认编辑空间，生成一条初始化导入审计记录。

脚本必须可重复执行：同一源文件摘要不重复导入；如目标内容已被人工修改，导入必须停止并报告冲突。

### 12.2 数据质量注意事项

当前原子知识点文档明确说明，部分教材页码、例题编号和练习编号尚需正式教材核对。因此初始导入可以缺少页码，但发布校验应明确标记为风险，不伪造教材页码和题目原文。

## 13. 测试方案

### 13.1 单元测试

- `canonical_id`、枚举和必填字段校验。
- 五级父子关系校验。
- 前置关系成环检测。
- 平行/交叉关系去重。
- HMAC 签名、时间窗口、Nonce 重放校验。
- 发布批次摘要冲突校验。

### 13.2 集成测试

使用 MySQL 8 测试库验证：

- 草稿保存与乐观锁冲突。
- 批量导入整批成功和整批回滚。
- 发布后开放接口只读到新正式版本。
- 回滚生成新版本且历史版本不变。
- 未选中的草稿变更不进入本次快照。

### 13.3 契约和验收测试

- 由 OpenAPI 生成接口契约并做响应字段校验。
- 验证 `canonicalId`、数组类型、分页和错误码。
- 验证四个正式查询接口在指定历史 `releaseVersion` 下结果稳定。
- 压测树查询、检索、批量详情、发布校验四条主路径。

## 14. 实施顺序

1. 初始化 FastAPI、SQLAlchemy、Alembic、配置和统一错误处理。
2. 建立教材版本、知识对象、词项、目录和映射表。
3. 完成 Markdown/Excel 预校验和初始数据导入。
4. 完成知识树、知识对象、映射和关系管理接口。
5. 完成发布批次、候选快照、校验、正式发布和历史预览。
6. 完成回滚、审计、任务 worker 和导出。
7. 完成开放只读接口、HMAC、限流和缓存头。
8. 完成 MySQL 8 集成测试、压测、备份恢复演练和上线检查。

## 15. 需要在开发前确认的事项

- 公司是否已有 SSO/OIDC；若有，V1 不另建本地账号密码体系。
- 内部网关是否已提供 HTTPS、AppKey 限流和审计能力；已有能力直接复用。
- 政策规则首批数据来源、规则版本和维护责任人。
- 正式教材核对后的页码、例题编号和练习编号是否纳入 V1。
- 导出文件的存储位置、保留时间和公司数据分级要求。

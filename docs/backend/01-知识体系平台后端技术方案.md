# 知识体系平台后端技术方案

> 版本：V1.0
> 对齐产品文档：知识体系平台 PRD V3.6
> 适用范围：人教版 2024 数学，一、二年级上下册
> 文档职责：说明系统如何实现；接口路径、字段和错误码以接口契约文档为准。

## 1. 目标与范围

### 1.1 后端目标

后端为运营后台和未来 App 提供同一套知识内容基础设施：

- 管理员维护原子知识点；
- 管理员维护教材目录与知识点的多对多映射；
- 管理员独立维护知识点之间的前置、后继、平行、交叉关系；
- 以知识库为发布边界，生成不可变正式版本；
- App 只能读取正式版本，不能读草稿；
- 保留历史版本、差异、回滚和审计记录。

### 1.2 V1 实现范围

- 人教版 2024 六三制小学数学一年级、二年级上下册；
- 三个管理菜单：知识库、知识列表、知识关联；
- 一个知识库对应一个年级/学期、学科和教材版本；
- 教材原始目录导入后只读展示，知识库草稿负责建立“目录节点 → 多个原子知识点”映射；
- 原子知识点字段严格以当前 Excel 为边界：
  canonical_id、type、name、grade_term、scope、ocr_signals、exercise_signature；
- 关系字段严格围绕四类关系：前置、后继、平行、交叉；
- 知识库状态：pending、published、offline；
- 知识点和知识关联状态：pending、published；
- 当前版本只有管理员一种身份，管理员拥有全部后台权限。

### 1.3 V1 不实现

- 三年级及以上内容；
- 独立知识点组对象；
- 领域、主题等额外运营层级；
- 知识点图形化编辑；
- 原子知识点停用或知识关联下线；
- 认知层级、重要程度、别名、核心关键词、衍生关键词、易错词/易错点、解题思路特征、场景结构特征、数值特征；
- 策略规则和政策映射；
- 题库、OCR 识别、题目最终匹配、学生学习记录和推荐算法；
- 多角色审批流；
- 为 V1 引入微服务、Redis、消息队列、搜索引擎或分库分表。

## 2. 技术决策

| 项目 | V1 决策 |
| --- | --- |
| 服务形态 | Python 模块化单体 |
| Web 框架 | FastAPI |
| Python | 3.9+ |
| ORM/迁移 | SQLAlchemy 2.x + Alembic |
| 数据库 | MySQL 8 / InnoDB / utf8mb4 |
| 驱动 | PyMySQL |
| 校验 | Pydantic + 领域服务 |
| Excel | openpyxl |
| 后台鉴权 | SSO/OIDC 或受控会话，当前只映射管理员 |
| App 鉴权 | AppKey + HMAC-SHA256 |
| 异步任务 | MySQL 任务表 + 独立 worker |
| 部署 | HTTPS 网关/Nginx → FastAPI → MySQL |

V1 内容量和写入并发有限，模块化单体可以在一个事务内完成草稿保存、发布快照和审计。只有题库同步或开放查询出现独立性能瓶颈时，才考虑拆分服务。

## 3. 系统边界

### 3.1 读写边界

- 管理端读写当前草稿数据，不直接改正式快照。
- App 只读 release_version 快照，不读取草稿表。
- 发布以知识库为事务边界，一次生成一个完整正式版本。
- 下线只改变知识库当前可用状态，不删除历史正式版本。
- 指定历史 releaseVersion 时，可读取历史正式快照；默认查询不返回下线知识库。

### 3.2 一致性原则

- 正式版本只追加，不更新、不删除。
- 知识点和关系不单独发布；它们只有进入至少一个知识库正式版本后才被视为已发布。
- 知识点或关系保存修改时只生成新草稿修订，不影响 App。
- 关联关系由前置关系反向计算后继关系，避免双向写入不一致。
- 所有写操作使用 row_version 乐观锁。
- 发布、回滚、下线和删除均写审计日志。
- 数据库事务内不调用远端 HTTP、对象存储或其他慢服务。

### 3.3 标识与时间

- 内部主键使用 BIGINT UNSIGNED。
- 对外长期引用使用不可变 canonical_id；canonical_id 是后端生成的以 1 开头的 8 位纯数字字符串，知识点删除后 ID 永不复用。
- 关系使用稳定 relation_id，两端和关系类型建立规范化唯一约束。
- 数据库存储 UTC DATETIME(3)，接口返回 ISO 8601。
- 后台 API 使用 camelCase，数据库使用 snake_case。

### 3.4 下拉选项和资源来源

不提供一个包含所有下拉数据的通用 options 接口，也不建立一个承载所有业务选项的万能字典表。选项按业务归属返回：

- 固定业务枚举由后端代码和接口契约维护：知识点类型、内容范围、关系类型、知识库/知识点/关系状态和发布类型。接口传稳定 key，前端展示 value。
- 学科和年级/学期是 V1 的教材域固定选项。稳定 key 由后端初始化配置维护，例如 math、g1_t1；展示 value 为“数学”“一年级上册”。
- 教材是 textbook_edition 资源。edition_code 是 key，edition_name 是 value，并携带 subjectCode、gradeTermCode；前端先选择学科和年级，再按条件查询教材。
- 教材目录是 catalog_node 资源，由教材导入产生；选择教材后调用目录接口，不作为通用字典选项。
- 知识库关联中的知识点候选使用知识列表接口的 `candidateForKnowledgeBaseId` 上下文查询，按 `pageNum`、`pageSize` 分页，不预加载全部 options。
- 状态是后端计算结果或操作结果，不作为可编辑的下拉选项。

前端不得自行创建或修改 key。需要新增学科、年级/学期或教材时，分别修改后端初始化配置或教材数据，不修改统一 options 接口。

## 4. 领域模型

### 4.1 模型关系

    textbook_edition
          │
          └── catalog_node（教材原始目录树）
                           │
    knowledge_base ─────────┼── knowledge_base_mapping
          │                │             │
          │                │             └── knowledge_object
          │                │
          └── release_version ── release_mapping
                                  release_knowledge
                                  release_relation

    knowledge_object ── knowledge_revision
    knowledge_relation ── relation_revision

知识库保存自己的目录映射草稿；知识点和知识关联是全局原子对象，但只有被某个知识库发布后才进入正式消费范围。

### 4.2 知识库

知识库是 App 选择“年级/学科/教材”后使用的发布单元。subject 和 grade_term 在数据库中保存稳定 key，展示名称由选项资源返回。

核心属性：

- knowledge_base_id
- name
- grade_term
- subject
- textbook_edition_id
- status
- current_release_id
- row_version

知识库草稿只保存当前待发布的目录映射和基础信息。发布成功后，生成不可变 release_version，并更新该知识库自己的正式版本指针。不同知识库之间不共享当前正式版本指针。

### 4.3 教材版本与目录

教材版本和目录是教材原始资料，不是知识点业务对象。

- textbook_edition：教材 key/value、学科 key、年级/学期 key、版本年份等。
- catalog_node：教材目录节点，使用 parent_id 表示父子关系。
- catalog_node 的层级由导入数据决定，不强行定义“领域/主题/知识点组”。
- title、source_key、source_path、sort_order 来自教材目录源数据。
- sort_order 仅保留教材原始顺序，不提供运营拖拽或排序接口。
- V1 管理接口和正式版本只返回教材根目录与单元，不展示或允许关联小节；数据库可保留源数据中的更深层节点作为导入兼容数据。
- 目录节点在 V1 由教材导入产生，后台只读展示和选择。

知识库编辑页选择左侧目录节点后，右侧查询该节点当前草稿映射的多个原子知识点。

### 4.4 原子知识点

knowledge_object 只保存稳定身份和当前修订指针；可编辑内容放入不可变的 knowledge_revision。

原子知识点当前 Excel 字段：

| Excel 字段 | 后端字段 | 存储方式 |
| --- | --- | --- |
| canonical_id | canonical_id | knowledge_object，唯一且不可改 |
| name | name | knowledge_revision |
| type | type | knowledge_revision |
| grade_term | grade_term | knowledge_revision，保存稳定 gradeTermCode |
| scope | scope | knowledge_revision |
| ocr_signals | ocr_signals | knowledge_revision，JSON 数组 |
| exercise_signature | exercise_signature | knowledge_revision，文本 |

pep24_path 不进入原子知识点编辑表，导入时只作为目录匹配建议；最终映射必须在具体知识库中确认。prerequisites 不直接写入知识点表，导入时转为待确认的关系草稿。

不在模型中增加其他字段。人工新建知识点不提交 canonical_id，由服务端生成全局唯一的以 1 开头的 8 位纯数字字符串；批量导入可提供符合规则的 ID。

### 4.5 知识点修订与状态

每次保存有实际变化时创建一个新的 knowledge_revision，旧修订不可修改。

知识点列表状态按“当前修订是否已进入任一知识库正式版本”计算：

- pending：当前修订尚未被任何知识库正式版本发布；包括首次创建和已发布知识点再次修改。
- published：当前修订已被至少一个知识库正式版本发布。

因此，知识点 v1 已发布后编辑生成 v2，状态立即变为 pending；App 继续读取各知识库已有正式版本，直到相关知识库发布包含 v2 的新版本。

“撤销草稿修改”不创建新修订，而是把当前编辑指针恢复到最近正式修订：

- 有正式修订且存在已保存草稿修改时显示入口；
- 恢复后状态回到 published；
- 首次创建、从未发布的知识点没有该入口，可直接删除草稿；
- 未保存的表单变化由“取消”处理。

### 4.6 知识库映射

knowledge_base_mapping 表示一个知识库草稿中，某个教材目录节点关联了某个原子知识点。

约束：

- 一个目录节点可以关联多个知识点；
- 一个知识点可以被多个目录节点和多个知识库引用；
- 取消关联只删除当前知识库草稿中的映射，不删除原子知识点；
- 映射没有独立的“下线”状态；
- 正式映射只存在于 release_mapping 快照；
- 映射表不提供运营排序字段和移动接口。

### 4.7 知识关联

knowledge_relation 保存稳定的关系身份，relation_revision 保存当前草稿修订。

关系类型：

- prerequisite：前置关系，保存 from → to 一个方向；
- parallel：平行关系，按两端 ID 规范化后只保存一条；
- cross：交叉关系，按两端 ID 规范化后只保存一条；
- successor：不落库，由前置关系反向查询。

关系说明 note 可选，供运营记录依据和边界。

约束：

- 不允许自关联；
- 不允许同类型、同两端重复；
- 前置关系不能形成循环；
- 新关系先是 pending；
- 已发布关系修改或删除生成新关系修订，状态变为 pending；
- 删除草稿关系时，未发布的新关系可以直接删除；
- 已发布关系的删除是草稿删除标记，发布后从新快照移除，历史快照保留；
- 不设置关系 offline 状态。

关系也支持“撤销草稿修改”。撤销删除会恢复原正式关系；撤销普通编辑会恢复最近正式修订。该操作写入审计记录。

### 4.8 正式版本

正式版本以知识库为范围，至少包含：

- 知识库基础信息；
- 教材目录节点快照；
- 目录节点与知识点映射；
- 当前纳入该知识库的原子知识点修订；
- 当前纳入该知识库的知识关联修订；
- 版本元数据、发布人、发布时间、来源版本和内容哈希。

版本是完整快照，不依赖当前草稿表。知识库 A 和 B 可以引用同一知识点的不同正式修订；一个知识库发布不会覆盖另一个知识库的正式快照。

## 5. 数据库设计

### 5.1 通用约定

- 所有业务表使用 InnoDB、utf8mb4、DATETIME(3)。
- 所有可编辑业务表包含 created_at、updated_at、row_version。
- 正式快照表只插入，不更新、不删除。
- JSON 只用于 ocr_signals 和导入错误明细等天然数组结构。
- 外键和唯一约束优先承担数据一致性，业务服务负责跨表规则。

### 5.2 textbook_edition

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| edition_code | 唯一教材版本编码 |
| edition_name | 教材名称 |
| subject | 学科 key，V1 为 math |
| grade_term | 年级/学期 key，V1 为 g1_t1、g1_t2、g2_t1、g2_t2 |
| version_year | 2024 |
| source_file_id | 原始目录文件 |
| status | active/inactive，教材数据管理状态 |

### 5.3 catalog_node

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| edition_id | 所属教材版本 |
| parent_id | 父目录节点，可为空 |
| level | 导入目录层级 |
| node_type | 源数据类型，不扩展额外产品层级 |
| source_key | 源目录稳定键 |
| source_path | 源目录路径 |
| title | 目录名称 |
| sort_order | 教材原始顺序，只读 |
| created_at / updated_at | 时间 |

唯一约束：edition_id + source_key。禁止普通后台接口修改目录层级和排序；目录变更通过受控导入任务完成。

### 5.4 knowledge_base

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| name | 知识库名称 |
| grade_term | 年级/学期 key |
| subject | 学科 key |
| textbook_edition_id | 教材版本 |
| status | pending/published/offline |
| current_release_id | 当前正式版本，可为空 |
| row_version | 乐观锁 |
| created_by / updated_by | 管理员 |
| created_at / updated_at | 时间 |

索引：grade_term + subject + textbook_edition_id + status。接口返回对应的展示名称，不把数据库 key 当作中文文案。

### 5.5 knowledge_object

| 字段 | 说明 |
| --- | --- |
| id | 内部主键 |
| canonical_id | 全局唯一、不可修改 |
| latest_revision_id | 当前草稿修订 |
| created_by / updated_by | 管理员 |
| created_at / updated_at | 时间 |

不保存知识点业务状态；状态由当前修订和正式快照查询计算。

### 5.6 knowledge_revision

| 字段 | 说明 |
| --- | --- |
| id | 修订主键 |
| knowledge_id | 原子知识点 |
| revision_no | 递增修订号 |
| name | 知识点名称 |
| type | 五类知识点类型 |
| grade_term | 年级/学期 |
| scope | core/supplement |
| ocr_signals | JSON 字符串数组 |
| exercise_signature | 题目结构摘要 |
| content_hash | 内容哈希 |
| created_by / created_at | 创建信息 |

唯一约束：knowledge_id + revision_no。修订创建后不可更新。

### 5.7 knowledge_base_mapping

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| knowledge_base_id | 知识库 |
| catalog_node_id | 教材目录节点 |
| knowledge_id | 原子知识点 |
| created_by / created_at | 创建信息 |

唯一约束：knowledge_base_id + catalog_node_id + knowledge_id。删除当前草稿映射即表示取消关联；历史正式映射由快照保留。

### 5.8 knowledge_relation 与 relation_revision

knowledge_relation：

| 字段 | 说明 |
| --- | --- |
| id | 关系主键 |
| relation_key | 规范化唯一键 |
| latest_revision_id | 当前草稿修订 |
| created_at / updated_at | 时间 |

relation_revision：

| 字段 | 说明 |
| --- | --- |
| id | 修订主键 |
| relation_id | 关系主键 |
| revision_no | 递增修订号 |
| operation | upsert/delete |
| relation_type | prerequisite/parallel/cross |
| from_knowledge_id | 起点 |
| to_knowledge_id | 终点 |
| note | 关系说明 |
| content_hash | 内容哈希 |
| created_by / created_at | 创建信息 |

relation_key 按关系类型规范化生成。前置关系保留方向；平行和交叉关系按较小 ID 在前生成。

### 5.9 正式快照表

release_version：

| 字段 | 说明 |
| --- | --- |
| id | 正式版本主键 |
| knowledge_base_id | 所属知识库 |
| version | 知识库内递增版本号 |
| base_release_id | 基础版本 |
| release_type | normal/rollback |
| source_release_id | 回滚来源版本，可为空 |
| content_hash | 完整内容哈希 |
| published_by / published_at | 发布信息 |
| reason | 发布或回滚原因 |

唯一约束：knowledge_base_id + version。

release_current：

| 字段 | 说明 |
| --- | --- |
| knowledge_base_id | 主键，同时是知识库 ID |
| release_id | 当前正式版本 |
| updated_at | 更新时间 |

该表按知识库保存指针，不能设计成全局单行。

release_catalog_node 保存正式版本实际使用的目录节点快照：release_id、catalog_node_id、parent_id、level、title、source_path、sort_order。

release_mapping 保存正式版本中的目录映射：release_id、catalog_node_id、knowledge_id、canonical_id。

release_knowledge 保存正式版本使用的知识点修订：release_id、knowledge_id、canonical_id、revision_id。revision_id 指向不可变修订，历史版本不受后续编辑影响。

release_relation 保存正式版本中的有效关系：release_id、relation_id、relation_revision_id、关系类型和两端 canonical_id。删除关系不会写入新版本；通过新旧快照差异体现移除。

### 5.10 导入、审计与任务

import_job / import_row：

- import_job 保存文件、操作者、校验阶段、确认状态和统计；
- import_row 保存行号、原始字段、解析结果、错误信息；
- 预校验阶段不写正式业务表；
- 确认提交时在一个事务内创建知识点修订和待确认关系草稿；
- pep24_path 只保存在导入行或匹配结果中，不绕过知识库直接形成正式映射。

audit_log 记录登录、创建、编辑、导入、删除、取消关联、关系维护、撤销草稿、发布、下线、回滚等操作，包含 operator_id、action、object_type、object_id、before_json、after_json、affected_knowledge_base_ids、request_id、created_at。不得记录 Secret、完整签名和敏感请求体。

job 统一保存导入、导出、发布校验任务状态：queued/running/success/failed/cancelled。V1 发布写入和正式指针更新仍在 API 事务中完成。

## 7. 关键业务流程

### 7.1 新建知识库

1. 校验年级、学科、教材版本组合；
2. 创建 knowledge_base，状态为 pending；
3. 加载对应 catalog_node；
4. 运营在知识库草稿中为目录节点添加多个 knowledge_base_mapping；
5. 保存只影响草稿；
6. 发布后生成 v1，状态变为 published。

### 7.2 新建或编辑知识点

1. 创建接口在未提供 canonical_id 时生成以 1 开头的 8 位纯数字 ID；导入接口校验外部提供的同规则 ID；
2. 写入 knowledge_revision，状态查询结果为 pending；
3. 编辑已发布知识点时新增修订，不覆盖旧修订；
4. 查询列表同时返回当前草稿值、最近正式值、当前正式版本摘要和状态；
5. 撤销草稿时恢复到最近正式修订；
6. 删除只允许未发布且无知识库映射、无关系引用的草稿对象。

### 7.3 维护知识关联

1. 从全局知识点候选中选择主知识点和关系节点；
2. 校验自关联、重复关系和前置循环；
3. 创建或修改 relation_revision；
4. 已发布关系的删除写入 operation=delete 的草稿修订；
5. 撤销草稿恢复最近正式关系；
6. 关系只有在相关知识库发布后才进入 App。

### 7.4 发布知识库

发布校验至少检查：

- 知识库基础信息完整；
- 教材版本与年级/学科一致；
- 映射目录节点属于该教材；
- 每个映射的知识点存在有效当前修订；
- 知识点字段和关系类型合法；
- 关系端点属于本次知识库内容；
- 前置关系无循环；
- 没有乐观锁冲突。

发布事务：

1. 锁定知识库和 release_current；
2. 读取当前草稿、目录和关系；
3. 生成差异和内容哈希；
4. 插入 release_version 及全部快照行；
5. 更新该知识库的 release_current 和 current_release_id；
6. 设置知识库状态为 published；
7. 写发布审计；
8. 提交事务。

不在发布事务中逐行改写知识点或关系的“已发布”字段。它们的状态由当前修订是否出现在任一正式快照中计算，避免多个知识库之间互相覆盖。

### 7.5 下线知识库

- 仅已发布知识库可以下线；
- 更新知识库状态为 offline；
- 保留 current_release_id 和全部历史快照；
- App 默认查询过滤 offline；
- 指定历史 releaseVersion 时仍可读取正式快照；
- 下线不改变知识点和关系的全局状态。

### 7.6 回滚知识库

1. 选择该知识库的历史正式版本；
2. 创建以历史版本为来源的回滚发布候选；
3. 回滚候选只作用于当前知识库，不回写全局知识点草稿；
4. 预览差异并确认原因；
5. 发布时复制目标版本的目录、映射、知识点修订和关系快照；
6. 生成 release_type=rollback 的新版本；
7. 更新当前指针，历史版本保持不变。

## 8. API 设计范围

完整字段、枚举和错误码见接口契约；后端实现至少提供以下边界。

### 8.1 知识库和目录

- GET/POST /api/v1/admin/knowledge-bases
- GET/PATCH/DELETE /api/v1/admin/knowledge-bases/{id}
- GET /api/v1/admin/textbook-editions
- GET /api/v1/admin/textbook-editions/{editionCode}/catalog
- GET /api/v1/admin/knowledge-bases/{id}/mappings
- POST /api/v1/admin/knowledge-bases/{id}/mappings
- DELETE /api/v1/admin/knowledge-bases/{id}/mappings/{mappingId}

教材接口支持 subjectCode、gradeTermCode 筛选，并返回教材 key/value、学科和年级信息。不提供统一 options 接口、独立知识点组接口、目录移动接口、映射排序接口和全局教材映射接口。

### 8.2 知识点

- GET/POST /api/v1/admin/knowledge
- GET/PATCH/DELETE /api/v1/admin/knowledge/{canonicalId}
- POST /api/v1/admin/knowledge/{canonicalId}/draft:revert
- POST /api/v1/admin/imports
- GET /api/v1/admin/jobs/{jobId}
- GET /api/v1/admin/jobs/{jobId}/errors

知识点创建和编辑不接收教材单元字段。教材关联只通过知识库映射完成。知识点类型和范围使用接口契约中的固定枚举；知识库关联时通过本列表接口的 `candidateForKnowledgeBaseId` 按知识库上下文分页查询候选知识点。

### 8.3 知识关联

- GET/POST /api/v1/admin/relations
- GET/PATCH/DELETE /api/v1/admin/relations/{relationId}
- POST /api/v1/admin/relations/{relationId}/draft:revert

不提供关系下线接口和关系状态批量停用接口。

### 8.4 发布与历史

- POST /api/v1/admin/knowledge-bases/{id}/publish:validate
- POST /api/v1/admin/knowledge-bases/{id}/publish
- GET /api/v1/admin/knowledge-bases/{id}/releases
- GET /api/v1/admin/knowledge-bases/{id}/releases/{version}
- GET /api/v1/admin/knowledge-bases/{id}/releases/{version}/diff
- POST /api/v1/admin/knowledge-bases/{id}/releases/{version}:rollback
- POST /api/v1/admin/knowledge-bases/{id}/offline

发布接口以知识库 ID 为边界，不提供独立知识点发布和独立关系发布。

### 8.5 App 开放接口

- GET /api/v1/open/knowledge-bases：按年级、学科、教材查询当前有效知识库；
- GET /api/v1/open/knowledge-bases/{id}/content：读取当前正式快照；
- GET /api/v1/open/knowledge-bases/{id}/content?releaseVersion=...：读取指定历史正式快照；
- GET /api/v1/open/knowledge-bases/{id}/knowledge/{canonicalId}：读取正式知识点；
- GET /api/v1/open/knowledge-bases/{id}/relations：读取正式关系。

所有开放接口只从正式快照查询，并返回 releaseVersion。不实现范围判断接口、策略接口和草稿查询接口。

## 9. 权限与安全

### 9.1 当前版本

V1 只有 admin：

- 查看、创建、编辑、导入、删除知识点；
- 创建和维护知识库；
- 关联和取消关联知识点；
- 创建、编辑、删除、撤销知识关联；
- 发布、下线、回滚和查看审计。

后端每个写接口都执行管理员鉴权，不能只依赖前端隐藏按钮。

### 9.2 未来角色保留

文档可以保留 Editor、Publisher、Admin 的未来职责说明，但 V1 不实现角色拆分、审批流和权限矩阵。后续增加角色时，只在鉴权依赖和发布 Service 增加策略，不改变快照模型。

### 9.3 App 鉴权

- X-App-Key 识别调用方；
- X-Timestamp 限制请求时间窗口；
- X-Nonce 防重放；
- X-Signature 使用 HMAC-SHA256；
- Secret 只存服务端，不写日志和错误响应；
- 开放接口按 AppKey 限流。

## 10. 性能、运维和可观测性

- V1 列表使用 MySQL 分页、组合索引和必要的前缀匹配；不预先引入搜索引擎。
- 通过 knowledge_base_id + catalog_node_id、canonical_id、relation_key、release_id，以及 release_relation 的 relation_id + relation_revision_id 建立查询索引。
- 发布时一次批量写入快照，避免逐条 API 调用。
- 导入和导出使用任务表，文件使用短期有效下载地址。
- `make db-init` 在 Alembic 迁移完成后，复用导入 Service 导入 `seed_data/` 中的一、二年级 Excel 种子数据；种子导入幂等，包含知识点和前置关系，不自动创建教材目录映射。
- 日志包含 request_id、operator_id、knowledge_base_id、release_version 和耗时，不记录敏感信息。
- 监控 API 错误率、发布失败率、导入失败率、数据库连接池、慢查询和任务积压。

## 11. 测试与验收

### 11.1 必测业务规则

- 一个目录节点可以关联多个知识点；
- 同一个知识点可以被多个知识库引用；
- 创建或编辑知识点后状态为 pending；
- 当前修订进入任一知识库正式版本后状态为 published；
- 已发布知识点再次编辑后重新变为 pending；
- 撤销草稿恢复最近正式值，不影响其他知识库；
- 关系后继由前置反向计算；
- 关系不允许自关联、重复和前置循环；
- 取消知识库映射不删除原子知识点；
- 已发布知识点或被引用知识点不能硬删除；
- 发布生成完整不可变快照；
- 知识库 A 发布不改变知识库 B 的正式版本；
- 下线知识库默认不可被 App 查询，历史版本仍可按版本读取；
- 回滚生成新版本，不修改旧版本；
- 导入预校验失败不产生部分写入。

### 11.2 技术验证

- Alembic migration 可重复执行且可回滚；
- MySQL 外键、唯一约束和乐观锁冲突有测试；
- 发布事务中途失败时，正式版本指针不变化；
- 开放接口无法读取草稿；
- 非管理员无法调用管理端写接口；
- HMAC 时间戳、Nonce 和签名校验有效；
- Excel JSON 数组、空值、以 1 开头的 8 位数字 ID 和重复 ID 校验有效。

## 12. 实施顺序

1. 清理模型和迁移：去除旧状态及已取消字段，建立知识点/关系修订表；
2. 建立教材版本、原始目录和知识库映射；
3. 完成知识列表的增删改查、导入和撤销草稿；
4. 完成知识关联、循环校验、删除和撤销草稿；
5. 完成知识库发布、历史、下线和回滚快照；
6. 完成 App 正式查询接口；
7. 补齐管理员鉴权、审计、任务、限流和监控；
8. 用一年级、二年级 Excel 数据执行端到端验收。

实现时先同步接口契约，再修改 SQLAlchemy 模型、Alembic migration、Service、Schema、API 和测试；不在本方案批准前扩展三年级或其他内容字段。

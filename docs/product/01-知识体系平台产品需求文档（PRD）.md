## 1. 引言

### 1.1 项目背景

随着移动互联网技术在基础教育场景中的深度渗透，低龄段学生家长对精准化、同步化校内学习资源的需求持续提升。当前市面上的多数教育类 App 存在核心知识体系与校内教学进度适配性不足、知识点拆分颗粒度不符合教育规律、无法精准匹配不同版本教材内容等共性问题，导致产品无法有效辅助学生巩固校内课堂知识，难以满足用户的实际学习需求。

在此背景下，我们计划研发一款面向低年级学生的教育辅助 App，通过匹配教材知识点、提供符合教学进度的针对性训练题，解决现有产品的痛点。而支撑这一 App 高效运转的底层核心，正是一套结构规范、逻辑严谨、扩展灵活的知识体系 —— 它既需要锚定人教版教材的官方编写逻辑，保证与校内教学进度的高度适配；又需要具备足够的可扩展能力，支撑后续高年级、多版本教材的迭代需求；同时还要形成完整的知识关联网络，为 App 的三大核心功能提供技术支撑：一是知识点匹配，即根据用户的答题行为定位知识薄弱点；二是范围判断，即基于教材映射、课程范围和政策规则，为业务端识别不符合教学进度的题目提供依据；三是举一反三训练，即依托知识体系中的知识点关联关系，生成同场景、同解法的拓展训练题。

为实现这一目标，需要先搭建一套完整的知识体系内容管理平台，作为后续所有业务功能的底层支撑。该平台将承担知识内容的结构化录入、层级化组织、标准化校验、关联关系维护、版本管理及多端分发等核心功能，为移动端提供稳定、规范、可复用的知识数据接口。

本需求文档所描述的所有功能及交互逻辑，均基于用户提供的《知识体系架构设计报告》中的核心架构规则、层级拆分标准及技术支撑逻辑展开。V1.0 是报告中 1—3 年级整体规划的首期落地范围，先验证一年级、二年级上下册的内容维护和分发闭环；后续再扩展三年级及其他教材版本。

### 1.2 产品目标

本阶段的产品建设目标，是完成知识体系管理平台 V1.0 版本的上线交付，为后续低年级教育辅助 App 的正式运营筑牢底层知识支撑能力。具体落地目标分为四个维度：

1. **知识内容标准化**：严格以人教版小学数学 2024 审定新版（六三制）教材为依据，搭建覆盖小学一年级、二年级上下册的 V1.0 知识体系；将知识内容结构化拆解为 “领域 - 主题 - 单元 - 知识点组 - 原子知识点” 五级层级，并建立知识点与教材位置、政策规则的多对多映射关系，为后续 App 的知识点匹配、范围判断提供底层锚点。

2. **管理能力线上化**：为知识运营团队提供知识节点、原子知识点、教材映射、关联关系、发布批次和版本历史的维护能力，支持批量导入、结构校验、差异预览和可追溯发布；V1.0 保留最小的编辑、发布权限区分，不建设复杂的多级审批体系。

3. **支撑业务轻量化**：平台为后续业务后端提供已发布知识内容的查询接口，覆盖知识树、知识点检索、详情、映射和关联关系等场景；范围判断接口返回课程范围、学习进度和合规状态及其原因，不直接以单一布尔值替代业务判断。

4. **架构设计前瞻化**：在当前一、二年级的限定范围内保留版本和学段扩展能力；后续扩展时优先复用通用知识对象和关系模型，教材目录与知识点通过映射关系连接，具体影响范围以发布前校验结果为准。

### 1.3 业务范围

#### 1.3.1 范围内的业务

本阶段的功能开发，严格限定在支撑低年级教育辅助 App 上线的核心需求范围内，具体覆盖边界如下：

- **年级覆盖**：仅支持小学一年级、二年级上下册的知识内容管理，严格按照教育部课程标准及人教版教材的编写逻辑进行内容编排，暂不涉及三年级及以上、学前或其他学段的知识内容管理。

- **架构覆盖**：严格落地用户提供的架构设计报告中规定的五级知识层级架构，覆盖 “领域 - 主题 - 单元 - 知识点组 - 原子知识点” 全部五级节点的维护能力；五级架构的层级划分标准、命名规范、排序逻辑等，均与架构设计报告中的定义保持完全一致。

- **功能覆盖**：提供完整的知识内容全流程管理能力，涵盖五级知识节点的增删改查、原子知识点批量导入、知识结构可视化校验、关联关系批量维护、内容修改实时预览、版本化管理及一键发布等核心运营功能；同时，提供标准化的知识内容调用接口，支撑后续业务端的接入使用。

- **教材覆盖**：仅支持人教版小学数学 2024 审定新版（六三制）一年级、二年级上下册；本阶段不实现其他教材版本，但数据模型保留教材版本和教材位置映射能力。

#### 1.3.2 范围外的业务

为保证本阶段的开发进度，聚焦核心需求落地，以下业务内容将不会在 V1.0 版本中实现，后续将根据产品运营情况及用户需求优先级，在迭代版本中逐步落地：

- 不支持三年级及以上年级的知识内容管理，后续高年级内容将作为专属扩展分支，在迭代版本中按需补充。

- 不支持除人教版外的其他版本教材（如苏教版、北师大版等）的知识内容管理，后续将通过扩展分支的形式，在迭代版本中落地多版本适配能力。

- 不支持复杂的知识图谱可视化编辑及跨知识点关联分析能力，仅提供满足核心需求的前置 / 后继关联关系编辑功能。

- 不提供面向 C 端用户的任何功能或界面，所有功能仅服务于内部知识运营人员。

- 不建设复杂的多级内容审核流程；V1.0 至少区分“编辑”和“发布”权限，并保留发布、回滚、导入、批量停用等关键操作的审计记录。

- 不涉及题目资源的直接管理或维护，知识体系平台仅提供知识内容的管理能力，题目资源将在后续的题库管理系统中单独维护，通过 `canonical_id` 与知识体系建立关联。

### 1.4 名词术语定义

为保证所有参与方对需求文档的理解保持一致，避免因认知偏差导致的落地风险，本报告严格遵循架构设计报告中的核心概念定义，对涉及的专属业务名词进行明确约定：

- **知识体系**：支撑 App 所有核心功能的底层结构化知识网络，由 “领域 - 主题 - 单元 - 知识点组 - 原子知识点” 五级层级架构，以及连接原子知识点的前置、后继、平行、交叉等关联关系共同组成；既完整还原教材的章节体例，又补充支撑 App 智能化功能所需的精细化属性，是计算机可识别、算法可匹配、题库可依托的完整结构化知识网络。

- **五级架构**：知识体系的核心组织框架，遵循从上到下的逻辑层级划分，依次为一级领域、二级主题、三级单元、四级知识点组、五级原子知识点；这一架构完全锚定人教版教材的编写逻辑，保证了知识体系的规范性与校内适配性。

- **原子知识点**：知识体系中拆分的最小单元，遵循 “一个教学课时能讲透、不可再拆分” 的拆分标准；是后续知识点匹配、范围判断依据和举一反三训练的最小锚定单元，其拆分逻辑匹配教材的小节教学内容，是整个知识体系的底层基础。

- **知识点关联网络**：连接原子知识点的逻辑关系集合，包括前置、后继、平行、交叉四种核心关联类型；其中前置、后继关系允许跨年级和跨学期，平行关系表示同类并列内容，交叉关系表示跨主题的关联内容。关联关系用于提供匹配、补救和推荐依据，不单独决定题目是否超纲。

- **公共主干**：用于组织通用知识对象的基础分类和关系模型。具体教材目录、单元位置和版本差异通过映射关系维护，不将某一版教材的目录直接视为所有版本的固定主干。

- **扩展分支**：后续新增的教材版本或学段内容通过新增教材版本、教材目录和映射关系接入；能否复用已有知识对象，以教研审核和映射校验结果为准，不承诺完全不影响现有内容。

- **超纲清单**：由官方教育部门或权威教研机构发布的政策规则及典型问题集合。平台保存规则版本、适用范围、依据和映射关系，供业务端结合题目、教材版本和学习进度进行判断，不把“超纲”固定为知识点的永久属性。

- **Ant Design**：本平台优先采用的中后台 UI 组件库；具体组件、尺寸和交互由 UI/技术设计确定，不作为业务需求的唯一实现方式。

## 2. 总体架构设计

### 2.1 设计原则

知识体系平台的架构设计，需要严格遵循用户提供的架构设计报告中明确提出的核心设计准则，同时满足业务端的轻量化、可扩展、易维护等关键要求，具体分为五大核心维度：

1. **层级严谨原则**：必须严格落地报告中规定的五级知识层级架构，架构中的每一级节点的拆分逻辑、编排顺序、命名规范，都必须与人教版教材的编写体例、内在知识逻辑完全匹配；五级节点的父 / 子节点关联关系，必须完全符合教材的章节编排逻辑，保证知识体系与校内教学进度的高度适配性。

2. **结构稳定原则**：采用“通用知识对象 + 教材版本映射”的分层设计，将教材目录、知识对象和业务规则分开维护；新增版本或学段时优先增加映射和差异内容，必要时通过发布前影响分析确认对现有业务的影响。

3. **扩展灵活原则**：教材版本、册次、单元和小节以独立目录维护，知识对象通过映射关系连接到教材位置；后续新增教材版本或高年级内容时，完成目录、知识对象、映射和关系校验后再发布，不以“无需调整现有架构”作为上线前提。

4. **规范唯一原则**：知识对象使用跨教材稳定的 `canonical_id`，层级目录节点使用独立的内部 `node_id`；两者均需在各自作用域内唯一，不能把教材版本、册次或单元顺序编码进 `canonical_id`。属性字段、关联关系和教材映射均遵循统一数据规范，保证不同模块、不同技术体系间的识别一致性。

5. **支撑业务轻量化原则**：平台负责维护已发布的知识内容、教材映射、关系和规则依据；业务端负责结合题目内容、学生进度和业务策略完成最终匹配与范围判断。接口返回版本、状态和判断依据，避免把复杂业务决策隐藏在单一查询接口中。

### 2.2 知识层级结构设计

本平台严格采用用户提供的架构设计报告中规定的五级层级架构 + 关联网络的落地模式，架构的层级划分、逻辑顺序均完全匹配人教版教材的编写逻辑；其中，五级层级架构是知识体系的核心组织框架，关联网络是支撑 App 智能化功能的关键逻辑依托。

#### 2.2.1 层级划分明细

知识体系的五级层级架构从抽象到具体、从宏观到微观，依次分为一级领域、二级主题、三级单元、四级知识点组、五级原子知识点，每个层级的划分依据、核心作用及落地示例如下：

| 层级名称           | 层级说明                                                                                                                                                 | 对应教材依据                                                                       | 示例                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **一级领域**       | 知识体系的最顶层分类，严格对应课程标准及人教版教材的知识领域划分                                                                                         | 完全匹配人教版教材的四大知识领域划分，是教材编写时的核心逻辑分类                   | 数与代数、图形与几何、统计与概率、综合与实践                                               |
| **二级主题**       | 对同一领域内的知识，按照核心知识范畴进行的一步细分，是连接领域与单元的中间层级                                                                           | 以人教版教材的单元编排逻辑为参考，将同一领域内、知识逻辑相近的内容整合为同一主题   | 数的认识、数的运算、常见的量、测量、图形的认识、数据的收集与整理                           |
| **三级单元**       | 知识体系的核心组织节点，完全对应该教材的实际教学单元                                                                                                     | 与人教版教材的单元编排顺序、内容范围完全一致                                       | 100 以内的加法和减法、长方形和正方形、分数的初步认识                                       |
| **四级知识点组**   | 介于单元与原子知识点之间的一个过渡分类层级，是对单元内知识内容的进一步细化；将同一单元内、考查技能维度相同的知识点整合为一个组，便于后续的知识组织和检索 | 以人教版教材的小节内容编排逻辑为参考，将同一单元内的关联小节内容整合为一个知识点组 | 周长的认识、长方形和正方形的周长计算                                                       |
| **五级原子知识点** | 知识点拆分的最小单元，遵循 “一个教学课时能讲透、不可再拆分” 的标准；是后续知识点匹配和范围判断依据的最小锚定单元，其拆分逻辑需匹配教材的小节教学内容     | 匹配人教版教材中实际的最小教学内容单元                                         | 周长的定义、长方形周长公式推导、正方形周长公式推导、长方形周长公式应用、正方形周长公式应用 |
| **关联网络**       | 连接原子知识点的逻辑关系集合，包括前置、后继、平行、交叉四种核心关联类型；是支撑 App 知识匹配、范围判断辅助和个性化学习路径规划的关键逻辑依托                    | 以人教版教材的知识演进逻辑为依据，定义知识点之间的前置、后继关系                   | 长方形周长公式的前置知识是 “周长的定义”，后继知识是 “组合图形的周长计算”                   |

这一架构中，五级层级架构锚定人教版教材的章节体例和知识内在逻辑，保证知识体系的规范性和校内适配性；而关联网络的补充设计，则是为了赋能 App 的知识点匹配、范围判断辅助和举一反三训练，使相关能力具备可落地的技术支撑。

#### 2.2.2 扩展架构设计

为满足后续多版本教材、高年级内容的扩展需求，同时保证现有公共主干架构的稳定性，本平台采用 “公共基础主干 + 版本 / 学段专属扩展分支” 的分层扩展架构模式，将不同版本、不同年级的内容差异控制在局部分支内，保证底层核心架构的长期稳定性。

- **通用知识对象与教材目录**：通用知识对象负责表达概念、技能和问题模型；教材目录负责表达某一版本教材中的领域、主题、单元和小节。两者通过多对多映射关系连接，避免把当前教材目录误当成所有版本的固定主干。

- **版本 / 学段扩展**：对于其他版本教材或高年级内容，新增教材目录和差异化知识对象，并建立与已有知识对象的等价、部分覆盖或相关映射；具体复用范围需经过教研确认，不能只依靠别名或主题挂靠推断。

后续新增教材版本或高年级内容时，至少需要完成教材目录导入、知识对象复用或新增、教材映射、规则映射、关系校验和发布前影响分析。通过统一的数据模型复用技术能力，但不预设新增内容不会带来维护成本或业务影响。

### 2.3 功能架构设计

知识体系平台的核心定位是为知识运营人员提供高效、便捷的知识内容维护能力，为上层业务提供稳定、标准化的知识调用接口。结合用户的实际运营需求，平台的功能架构设计分为三大核心模块，覆盖知识维护、预览发布、接口支撑全流程：

```
知识体系平台

│   ├── 1.2 原子知识点维护

│   │   ├── 原子知识点单条录入/编辑

│   │   ├── 原子知识点批量导入/导出（支持Excel格式模板）

│   │   ├── 原子知识点多维度元数据属性维护

│   │   └── 知识点关联关系批量维护（前置/后继/平行/交叉）

│   ├── 1.3 知识树结构可视化管理
```

### 2.4 核心流程逻辑设计

知识体系平台的核心业务流程，需要保证知识内容从录入到正式发布的完整性、准确性和可追溯性。V1.0 不建设复杂的多级审核流，但保留编辑、发布权限区分、发布批次、自动校验、版本快照和回滚记录；核心业务流程如下：

```
\[开始] → \[登录系统] → \[选择操作模式]

├─→ \[知识树管理：维护五级架构节点]

│        └─→ \[原子知识点维护：录入/导入知识点元数据]

│                └─→ \[映射关系维护：绑定教材位置/政策规则]

│                        └─→ \[关联关系维护：设置前置/后继等关联逻辑]

├─→ \[内容预览：多模式检查知识结构及详情]

└─→ \[创建发布批次：选择本次变更内容]

       └─→ \[发布前系统校验：检查完整性/合法性/关系和映射]

       ├─→ 校验不通过 → \[返回编辑环节修改]

       └─→ 校验通过 → \[发布者确认]

               └─→ \[生成正式版本快照并切换正式版本指针]

                       └─→ \[结束]
```

V1.0 的“发布者确认”是最小发布审核环节，不要求多级审批；后续如增加更复杂的审核流程，可在发布者确认前增加审核节点。发布批次、版本快照、操作人、操作时间、变更内容和校验结果均需记录，便于问题排查和版本追溯。

## 3. 功能需求详述

### 3.1 知识树管理模块（核心维护层）

知识树管理模块是整个平台的核心功能模块，承担着所有五级架构节点、原子知识点、关联关系及映射关系的维护任务；后续业务端的所有知识数据，均来自该模块维护的内容。

#### 3.1.1 知识树结构维护

知识树结构维护是运营人员对知识体系的层级结构进行可视化编辑的核心入口，支持对五级架构的所有节点进行可视化的新增、编辑、查询、停用、排序及移动操作。

- **入口页面**：系统首页左侧菜单栏点击 “知识树管理”，右侧内容区将展示知识树的可视化结构。

- **页面布局**：建议采用左侧知识树、右侧详情编辑的双栏布局；具体分栏方式、比例和组件由 UI/技术设计根据实际内容密度与屏幕尺寸确定。

- **交互逻辑**：
  - 左侧知识树区域：默认以“折叠到二级主题节点”的状态展示当前教材版本目录；支持展开、收起、搜索和同层级排序；右键菜单提供“新增子节点”“编辑节点”“停用/废弃节点”“移动节点”等操作。

  - 右侧详情编辑区域：当用户在左侧知识树区域选中一个节点后，右侧区域展示该节点的可编辑属性；保存后进入当前编辑空间，发布后才进入正式版本。存在未保存内容时切换节点需提示确认。

- **功能约束**：
  - 节点的新增 / 编辑 / 停用操作，必须遵循五级架构的层级约束规则，即只能在相邻层级间建立父子关联关系；例如，二级主题节点的父节点只能是一级领域节点，三级单元节点的父节点只能是二级主题节点，以此类推，不能跨层级建立父子关联。

  - 节点停用或废弃时，系统需要先校验该节点下是否存在下级节点、教材映射、关联关系或正式版本引用；存在引用时不允许硬删除，只能停用/废弃并保留历史记录。空节点可从当前编辑空间移除。

  - 节点移动时，系统需要自动校验目标父节点的层级合法性；例如，四级知识点组节点的目标父节点只能是三级单元节点，不能将四级知识点组节点移动到二级主题节点下。

  - 五级原子知识点节点使用独立的内部节点标识挂载在四级知识点组下；新增原子知识点时必须明确所属 `groupNodeId`，五级节点只允许在同一四级知识点组下移动和排序，不允许移动到其他层级节点下。知识对象的 `canonical_id` 与五级目录节点 ID 分开管理。

  - 调整节点排序时，系统需要自动校验目标位置的层级合法性，仅支持在同一父节点下的同层级节点间进行排序调整，不能跨父节点调整节点排序；五级原子知识点仅支持在同一四级知识点组内排序。

#### 3.1.2 原子知识点维护

原子知识点是知识体系的最小粒度单元，也是后续业务端的核心数据锚点；运营人员需要在四级知识点组节点下，维护原子知识点的所有元数据属性，以及知识点之间的关联关系。

- **入口页面**：在知识树结构维护页面，选中一个四级知识点组节点后，在右侧详情编辑区域的 “知识点列表” 标签页中，展示该节点下的所有原子知识点；点击列表上方的 “新增原子知识点” 按钮，或操作列的 “编辑” 按钮，即可打开原子知识点的录入 / 编辑弹窗，进行详情维护。

- **页面布局**：弹窗或详情页用于维护原子知识点的元数据；录入字段按照“基础属性”“映射属性”“关联属性”三大核心维度分组，具体容器和尺寸由 UI/技术设计确定。

- **交互逻辑**：支持在知识点列表中，选择多个知识点后，点击 “批量导入” 或 “批量停用” 按钮，进行批量操作；已被正式版本或其他内容引用的知识点不提供硬删除，只能停用或废弃。列表上方提供 “搜索 / 筛选” 区域，支持按知识点名称、`canonical_id`、所属年级等关键维度进行检索，快速定位需要编辑的知识点；在录入 / 编辑页面中，分为 “基础属性”“映射属性”“关联属性” 三个步骤，运营人员可按需完成录入，系统在保存和发布校验时统一检查完整性；保存后保留当前编辑状态，并在列表中刷新最新内容。

- **字段规范**：原子知识点的元数据字段设计，严格参考教育部教育信息化技术标准委员会发布的《基础教育知识图谱建设技术规范》，结合低年级教育辅助 App 的实际业务需求，核心字段规范如下：

> **V1 字段实施补充**：稳定知识对象 ID 使用 `canonical_id`。它跨教材复用，不包含出版社、年份、册次和单元顺序；当前命名采用小写字母、数字和下划线组成的语义段，并使用英文句点分隔，例如 `m.num.count.1_100`、`m.shape.solid.cuboid`、`m.problem.money.total`。教材版本、册次、单元、小节和页码统一记录在 `pep24_path` 等教材映射关系中，允许一个知识对象映射多个教材位置。名称调整、教材位置变化或发布版本变化不修改 `canonical_id`；只有学习目标、数值范围或解法要求发生实质变化时，才新建知识对象 ID，并通过 `related` 或 `prerequisite` 建立关系。ID 停用后不得重新分配给其他知识对象。领域模型字段名为 `canonical_id`；若接口采用 camelCase，则统一映射为 `canonicalId`，不得再生成或使用 `knowledgeCode`。表中的“超纲标识”和“超纲映射编码”仅作为兼容展示字段，不作为最终范围判断；实施时增加“课程范围”和“政策规则映射”，记录规则版本、依据和适用条件。难度等级按认知层级理解，题目难度由题库或业务端单独维护。别名、关键词和衍生词按数组或独立关系记录，不使用逗号分隔字符串承载语义。

上述字段的约束规则及取值范围，完全参考架构设计报告中的相关定义，保证了数据规范性与业务适配性。

**稳定 ID 生命周期与校验**：

- 新建知识对象时生成 `canonical_id`；创建后不可修改、不可复用，不因名称调整、教材改版、教材位置变化、发布或回滚而改变。
- 新增教材版本时，优先复用学习目标相同的 `canonical_id`，通过新的教材映射记录版本差异；只有学习目标、数值范围或解法要求发生实质变化时，才新建 `canonical_id`。
- 停用或废弃知识对象时保留其 `canonical_id`、历史版本和关系记录；业务端引用使用 `canonical_id + releaseVersion`，不使用教材路径或展示名称作为长期引用键。
- 发布校验必须检查 `canonical_id` 的全局唯一性、命名格式、重复回收、关联引用存在性，以及教材映射与知识对象类型是否匹配；教材映射重复不等同于 `canonical_id` 重复。

- **批量导入 / 导出功能**：平台支持标准 Excel 模板导入和导出。导入流程为“上传文件 → 预校验 → 展示错误报告 → 确认提交”，预校验阶段不修改正式或草稿数据；只有运营人员确认提交后，才将整批数据写入当前编辑空间。单次导入最多支持 1000 条知识点数据，失败时返回行号、字段、原因和修复建议，不执行部分写入。导出内容标明教材版本、编辑空间或正式发布版本，避免把不同版本的数据混用；导入、导出和批量停用均记录操作日志。

  - **Excel 导入模板**：主工作表固定使用 `knowledge_points`，表头为 `canonical_id`、`type`、`name`、`grade_term`、`scope`、`pep24_path`、`ocr_signals`、`exercise_signature`、`prerequisites`。其中 `ocr_signals` 和 `prerequisites` 使用 JSON 数组字符串，禁止使用逗号拼接数组；`prerequisites` 为空时填写 `[]`。可附带 `prerequisites` 关系明细工作表，但后端以主工作表为导入主数据。

  - **批量停用**：已被正式版本或其他内容引用的知识点不提供硬删除，只能批量停用或废弃；批量停用必须返回逐项结果并写入审计日志。

#### 3.1.3 知识点映射关系维护

知识点映射关系是连接知识对象、教材位置和政策规则的核心逻辑，是后续 App 获取候选知识点和范围判断依据的重要基础。运营人员完成知识对象录入后，在“知识点映射关系维护”功能中批量维护教材映射和政策规则映射。

- **入口页面**：在知识树管理页面的右上角，点击 “更多操作” 下拉菜单，选择 “知识点映射维护” 选项，即可进入映射关系维护页面。

- **页面布局**：采用标签页分别展示“教材章节映射”和“政策规则映射”；映射区域先选择教材版本或规则版本，再展示对应的教材位置、知识点和关系详情。

- **交互逻辑**：
  - 教材章节映射：运营人员选择教材版本和教材位置后，右侧展示该位置已映射和未映射的知识对象；支持批量绑定或解除映射，并为每条映射填写映射类型（引入、练习、复习、应用）、页码和依据。同一知识对象允许映射多个教材位置。

  - 跨教材对齐信息：教材映射至少记录 `textbook_edition`、`textbook_path`（人教版当前可使用 `pep24_path`）、`alignment_type`、`edition_label` 和 `edition_keywords`；`alignment_type` 取 `equivalent`、`narrower`、`broader`、`related`，用于说明同一 `canonical_id` 在不同教材中的对齐关系。

  - 政策规则映射：运营人员选择规则版本、适用年级或学段后，为知识点绑定政策规则或典型问题，并填写适用条件和依据。解除教材映射不自动删除政策规则映射；两者是独立关系。

- **功能约束**：
  - 教材章节映射的对象必须是具有 `canonical_id` 的知识对象；`review_set`、场景标签、方法标签和易错点标签不创建新的 `canonical_id`，通过集合映射或标签关系维护。

  - 一个知识对象可以映射到多个教材章节位置；同一教材位置也可以关联多个知识对象，但同一知识对象与同一教材位置的同类型映射不可重复。

  - 政策规则映射可以独立维护，但发布前必须检查规则版本、适用条件和教材版本是否完整。

  - V1 不建设独立的政策规则 CRUD 页面；政策规则版本和规则正文由初始化数据或管理员配置提供，平台前端只维护知识对象与政策规则的映射、适用条件和依据。后续如需运营人员维护规则正文，再单独增加政策规则管理模块。

  - 解除教材章节映射关系时，不自动删除政策规则映射；系统只提示可能影响范围判断，并在发布校验中定位缺失或冲突。

#### 3.1.4 知识点关联关系维护

知识点关联关系是支撑 App 范围判断辅助、个性化学习路径规划的重要逻辑依据，运营人员可以在 “知识点关联关系维护” 功能中，对原子知识点的前置、后继、平行、交叉四种关联关系进行批量维护。

- **入口页面**：在知识树管理页面的右上角，点击 “更多操作” 下拉菜单，选择 “知识点关联维护” 选项，即可进入关联关系维护页面。

- **页面布局**：采用 Ant Design 的`Card`组件进行垂直布局，上方为知识点搜索筛选区域，支持按知识点名称、`canonical_id`、所属年级等维度快速检索；下方为关联关系编辑区域，分为左右两个等分区域，左侧为 “当前知识点” 区域，展示用户选中的知识点的所有基础属性；右侧为 “关联知识点编辑” 区域，采用`Tabs`组件分四个标签页，分别维护前置、后继、平行、交叉四种关联关系。

- **交互逻辑**：运营人员在搜索区域找到需要维护的原子知识点后，在右侧区域的四个标签页中，分别点击 “添加关联” 按钮，从平台的所有原子知识点列表中，选择需要建立关联的知识点，添加到对应的关联列表中；完成关联添加后，点击 “保存” 按钮，系统将校验关联关系的合法性，校验通过后将同步更新知识树中的关联关系数据。

- **功能约束**：
  - 关联关系的维护对象只能是五级原子知识点，不支持对其他层级节点进行关联维护。

  - 关联关系必须逻辑严谨，禁止建立不合理的关联关系；例如，不能将 “长方形周长公式应用” 设置为 “周长的定义” 的前置知识。

  - 前置、后继关联关系允许跨年级、跨学期，但必须记录关系依据和适用教材范围；平行关系默认限制在同一知识点组或同类知识对象之间；交叉关系允许跨主题，需填写关联说明和关系依据。

  - 若 A 知识点是 B 知识点的前置知识，那么 B 知识点必须是 A 知识点的后继知识；系统将自动双向建立关联关系，不需要运营人员手动重复设置。

  - 前置、后继关系在界面上双向展示，但系统只保存一条带方向的关系记录；删除前置关系时同步更新后继展示。发布校验只检查前置关系是否成环，不把平行或交叉关系误判为循环。

### 3.2 内容预览与发布模块（内容校验层）

运营人员完成知识内容的维护后，需要通过预览功能检查内容的实际展示效果，通过发布功能生成业务端可读取的正式版本；该模块是保证知识内容的准确性、合法性和可追溯性的关键环节。

#### 3.2.1 知识内容预览

运营人员在完成知识树结构、原子知识点及映射关系的维护后，需要通过预览功能，检查知识内容的实际效果和层级逻辑；平台提供三种不同的预览模式，满足运营人员的不同校验需求。

- **入口页面**：在知识树管理页面的右上角，点击 “预览” 按钮，即可进入知识内容预览页面。

- **布局与交互逻辑**：左侧为知识树或教材目录预览区域，右侧为详情区域；运营人员可切换“当前编辑空间”和“已发布版本”，查看对应的知识树、元数据、教材映射、政策规则映射和关联关系。原子知识点详情展示范围判断相关的规则依据，不展示一个未经解释的“超纲”结论。

- **预览模式**：
  - **按章节预览**：按照选定教材版本的章节顺序，展示教材目录及其关联知识点，便于检查知识点映射的完整性和准确性。

  - **按年级预览**：运营人员选择年级、学期和教材版本后，系统过滤对应目录、知识点和映射关系，便于检查指定范围的内容完整性。

  - **按知识点类型预览**：运营人员可以在预览页面顶部的下拉菜单中，选择一个知识点类型，系统将自动过滤出该类型下的所有知识点，按教材章节顺序展示知识树结构，便于运营人员快速检查特定类型知识点的内容规范性。

#### 3.2.2 发布管理

运营人员完成知识内容的维护后，通过发布批次将选定的变更生成正式版本；平台在发布前自动校验完整性、关系、映射和引用，只有通过校验并经发布者确认的内容才能生成正式版本。

- **入口页面**：在知识树管理页面的右上角，点击 “发布” 按钮进入发布管理页面；运营人员先创建发布批次，再选择本次要发布的变更内容。没有待发布变更时按钮保持禁用。

- **页面布局**：采用 Ant Design 的`Card`组件进行垂直布局，从上到下依次为：发布信息编辑区域、更新内容预览区域、发布校验结果区域、操作按钮区域；所有区域的标题和内容左对齐，操作按钮区域采用右对齐布局，保证信息层级清晰。

- **权限约束**：编辑者可以创建和修改草稿、创建发布批次并发起校验；发布者可以确认发布和创建回滚批次；管理员可以停用内容、管理版本和处理异常。V1.0 不要求更细的字段级权限。

- **交互逻辑**：
  - 运营人员进入发布页面后，系统展示当前编辑空间中尚未进入正式版本的变更内容；运营人员可按节点、教材版本、变更类型筛选并加入发布批次，再填写版本说明、修改原因和影响范围。

  - 点击 “开始校验” 按钮后，系统将自动对当前发布批次中的知识内容进行多维度合法性校验；校验完成后，系统将在发布校验结果区域，以列表形式展示所有校验结果，包括校验通过的内容、存在的风险点及校验不通过的错误点。

  - 若校验结果中存在错误点，运营人员需返回编辑并重新校验；若只有风险点或完全通过，具备发布权限的发布者可以点击 “确认发布”，系统生成不可变的正式版本快照并记录发布日志。未加入本批次的其他草稿不受影响。

- **发布校验规则**：系统在发布前，将强制校验以下核心维度的合法性，只有完全通过校验的内容，才允许被正式发布：
  - 知识树的五级架构是否存在不合法的跨层级父子关联关系。

  - 所有知识对象的必填字段是否存在缺失值，`canonical_id` 是否符合命名规范且不存在重复、复用或非法变更。

  - 关联关系中的 `canonical_id` 是否存在于当前编辑空间或已发布版本，且关系类型与知识对象类型、方向约束相匹配。

  - 原子知识点是否存在必要的教材映射；允许一个知识点映射多个教材位置，但同一知识点与同一教材位置的同类型映射不得重复。

  - 知识对象的关联关系逻辑是否合法；仅检查前置关系是否成环，平行和交叉关系不按有向环处理，并检查跨年级关系是否填写依据。

  - 存在前置关联关系的知识点，其前置知识点是否存在于当前编辑空间或已发布版本；“未掌握”不作为发布错误，也不直接判定为超纲。

  - 若本次发布修改了已被引用的内容，系统展示影响范围并要求发布者确认；发布版本通过版本快照和关系记录保持引用可追溯，不因业务端已引用就禁止正常回滚。

  - **发布回滚**：发布完成后，具备权限的运营人员可选择一个保留的正式版本创建回滚发布批次；系统先预览该版本与当前版本的差异，确认后生成新的正式版本快照并切换正式版本指针。回滚不删除中间版本，也不因业务端引用过而禁止操作；业务端通过 `releaseVersion` 或 ETag 重新获取稳定内容，平台不强制逐个推送业务端缓存更新。

#### 3.2.3 版本历史管理

平台对所有正式发布的知识内容版本进行历史记录归档；运营人员可以查看版本差异、预览历史快照，并通过创建新的回滚发布批次恢复历史内容。

- **入口页面**：在知识树管理页面的右上角，点击 “更多操作” 下拉菜单，选择 “版本历史” 选项，即可进入版本历史管理页面。

- **页面布局**：采用 Ant Design 的`Table`表格组件进行列表布局，默认按版本发布时间倒序排列，展示所有历史版本的核心信息；表格的每条记录对应一个历史版本，包含版本号、版本说明、发布人、发布时间、修改内容摘要等核心字段；点击记录左侧的展开箭头，可以查看该版本与上一版本的详细内容差异。

  - **交互逻辑**：运营人员可以在列表中选择任意一个历史版本，点击“预览”查看历史快照；若需要恢复该版本，点击“创建回滚批次”，系统展示与当前版本的差异和影响范围，确认后生成新的正式版本，修改内容摘要为“回滚到版本 X”。

- **功能约束**：
  - 正式版本和操作记录按公司数据保留策略归档；列表可分页展示，历史快照在归档后仍可按权限预览。是否允许从归档版本创建回滚批次由数据保留策略决定，不再设置“最近3个/10个”的重复限制。

  - 仅允许从正式发布过的版本创建回滚批次，待发布或编辑中的临时版本不支持回滚。

  - 若历史版本被后续内容或业务端引用，系统展示影响范围并要求发布者确认，不要求删除后续引用内容。

  - 回滚操作生成新的发布记录，保留原版本、回滚操作者、回滚原因和新版本差异，确保审计链完整。

### 3.3 开放接口模块（业务支撑层）

为支撑后续业务端的知识内容调用，平台提供已发布知识内容的标准查询接口。接口返回教材版本、发布版本、内容状态和必要的映射依据；题目 OCR 解析、知识点最终匹配和学生学习状态由业务端负责。所有接口设计都遵循统一的 HTTP/JSON 规范，详细请求参数和返回结构另见《知识体系平台接口契约文档》。

本阶段计划开放以下核心接口，满足业务端的常见知识获取需求：

| 接口名称                  | 接口功能                                                                                           | 请求方法 | 适配业务场景                                                |
| ------------------------- | -------------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------- |
| 获取知识树结构            | 返回完整的五级知识树架构，支持过滤指定年级、教材版本的知识树结构                                   | GET      | 后续 App 的知识点匹配、学习路径规划、章节维度内容展示等场景 |
| 知识点多维度检索          | 根据关键词、年级、知识点类型、认知层级、重要程度等条件过滤已发布知识点集合；返回候选结果，不承诺直接完成题目匹配 | POST     | 后续业务端的候选召回和内容搜索             |
| 批量获取知识点详情        | 根据传入的 `canonical_id` 集合和发布版本，返回知识点元数据、教材映射、政策规则映射和内容版本信息 | POST     | 后续业务端的知识点详情展示和题目标签读取   |
| 获取知识点关联关系        | 返回指定 `canonical_id` 的所有前置、后继、平行、交叉关联知识对象 ID                                         | GET      | 后续 App 的范围判断辅助、学习路径规划、相关知识点推荐等场景     |
| 获取年级 / 版本专属知识点 | 根据传入的年级、教材版本条件，过滤并返回符合要求的所有知识对象 `canonical_id` 集合                         | GET      | 后续 App 的章节训练、单元测试、同步练习等场景               |
| 获取范围判断依据          | 根据知识点、题目上下文、教材版本和规则版本返回课程范围、学习进度和合规状态的判断依据           | POST     | 后续业务端的范围判断、训练题过滤和内容推荐         |

所有接口的交互逻辑，均采用“请求鉴权 + 参数校验 + 数据处理 + 统一响应”的标准流程；管理端使用 SSO/OIDC 或受控会话 Cookie，开放接口使用 AppKey + HMAC 签名，Secret 只保存在服务端，并校验时间窗口和 Nonce；接口使用 HTTPS 和 UTF-8 JSON。接口的详细调用规则、返回参数示例、错误码规范等内容，以后端技术方案和《知识体系平台接口契约文档》为准。

## 4. 非功能性需求

### 4.1 环境约束

知识体系平台是内部核心业务系统，其网络环境、浏览器适配及部署架构要求，需严格符合公司内部中后台系统的技术标准，保证运营人员的使用体验和系统兼容性：

- **网络环境要求**：平台部署在公司的内部专业运维环境中，仅允许内网环境下的运营人员进行访问，不提供外网域名或端口；后续业务端与知识体系平台的接口通信，均通过内部专属的网络通道进行，不允许经过外网传输；若运营人员需要在外部网络访问，必须先接入公司的 VPN 网络，通过内网域名或端口进行访问。

- **浏览器适配要求**：支持公司前端技术栈和设计系统所覆盖的主流浏览器；不支持 IE 及其他已停止维护的浏览器。具体浏览器版本以技术方案和上线时的公司兼容性基线为准；不符合要求时给出升级或更换浏览器的提示。

- **部署架构要求**：平台采用公司现有的前后端部署和数据库基础设施。V1.0 不强制微服务、读写分离、分库分表或多副本集群；在当前运营规模下优先保证数据备份、版本可恢复和接口稳定，具体部署方案由技术设计文档根据实际负载确定。

### 4.2 性能需求

知识体系平台的性能，直接影响运营人员的维护效率，以及后续业务端的接口调用稳定性；结合用户的实际使用场景，V1.0 版本需满足以下性能指标要求：

- **系统响应时间**：在约定的运营数据量和网络环境下，常规查询与编辑操作以 P95 响应时间为验收指标；批量导入和发布校验允许异步执行并展示进度。超过阈值时必须提供加载状态、取消或重试提示，并防止重复提交。具体阈值在技术方案和压测后确定。

- **数据处理性能**：批量导入、批量停用、批量移动和发布校验均需支持进度反馈、失败明细和重试；V1.0 单次批量操作暂以 1000 条作为容量基线，具体处理时限在技术方案和压测后确定。

- **并发处理性能**：以 V1.0 预计运营人员规模和业务端调用量作为压测基线；在目标并发下，常规操作需满足约定的 P95 延迟、错误率和可用性指标，具体数值由技术方案和压测确定。

- **接口性能要求**：开放接口在约定的业务并发和数据规模下，以 P95 延迟、错误率和可用性作为验收指标；批量数据查询支持分页和版本过滤，必要时异步生成。具体数值在技术方案和压测后确定。

- **容量规划要求**：V1.0 以一年级、二年级上下册的实际内容规模为容量基准，支持后续数据增长和历史版本归档；具体容量、备份周期和扩容方式由技术方案结合实际数据量确定。

### 4.3 安全性需求

知识体系平台的内容是 App 的核心底层支撑，需要严格保证访问安全；所有的安全校验逻辑，均需遵循公司内部的统一安全规范。

- **数据安全要求**：知识内容、操作记录和配置数据按公司数据分级策略管理；传输必须使用 HTTPS，导出文件需按权限控制并设置有效期，必要时使用公司统一加密方案。只有涉及敏感信息的字段才进行字段级加密，避免加密后无法检索和校验。

- **接口安全要求**：所有开放接口必须采用专业的鉴权机制，校验调用方的合法身份；所有接口的请求参数，需要进行严格的参数校验，过滤掉非法的参数值、特殊字符，防止注入攻击；接口的请求频率，需要设置严格的限流阈值，避免被恶意调用或暴力破解；接口在处理批量数据请求时，需要对单次请求的最大数据量做严格限制，避免数据量过大导致接口响应超时。

- **操作安全要求**：V1.0 至少记录登录、导入、编辑、映射、关联、停用、发布、回滚和导出操作，包含操作人、时间、操作类型、对象、变更摘要、结果和 requestId；重要操作需要二次确认。审计记录按公司审计平台要求留存，禁止记录 Secret、完整签名或敏感请求参数。

- **内容安全要求**：对面向用户的文本内容执行公司规定的内容安全校验；数学术语、教材原文和业务字段不因普通关键词命中而直接阻断，系统应展示命中位置和规则依据，由发布者确认或修改。

### 4.4 可用性需求

- **可用时间**：平台的可用时间为运营人员的正常工作时间，每天 9:00-21:00 必须保持正常可用；其他时间允许进行迭代更新或问题排查，但在更新或排查前，需要提前在运营团队的工作群内发布通知，且更新时间不得超过 1 小时；每月的正常可用时间占比不得低于 99.9%。

- **容错性要求**：平台需具备良好的容错性，在运营人员进行非法操作、提交校验不通过的表单或网络请求超时等场景下，系统需要在前端给出清晰、明确的提示，不能出现页面崩溃、白屏、无提示关闭或任意跳转等影响用户体验的情况；在后端服务出现短暂异常时，系统需自动进行重试，或返回合法的错误提示，不能出现数据不一致、请求挂起等影响业务的情况。

- **兼容性要求**：平台需严格遵循 Ant Design 的官方组件适配规范，在主流的适配浏览器版本、主流分辨率下，保持界面渲染效果、交互行为的完全一致性；在 1440px 及以上宽度的高清显示设备上，所有的页面元素不能出现排版错乱、重叠、溢出或模糊等视觉问题；在笔记类设备的小屏幕上，所有的页面元素需保持合理的缩放比例，内容区域自动出现垂直滚动条，保证内容的完整展示。

### 4.5 可扩展性需求

平台需要为后续高年级、多版本教材扩展预留数据和接口能力；具体扩展影响在新增内容时通过影响分析和回归验证确认，不预先承诺无需重构或无需修改核心代码：

- **架构扩展性要求**：教材版本、教材目录、知识对象、映射关系和政策规则独立维护；后续新增年级或教材版本时，支持新增目录和关系，并在发布前完成影响分析、校验和回归验证。

- **功能扩展性要求**：平台的所有功能模块采用低耦合设计；后续增加审核流程、角色权限管理、多语言管理、内容批量校验或第三方题库同步时，先通过技术方案评估影响范围，再按需扩展或调整现有模块，不预先承诺无需修改核心代码。

- **接口扩展性要求**：开放接口的设计需遵循向后兼容原则；新增参数、返回字段或接口版本时，应通过兼容性评估和契约测试，避免影响现有业务端调用。确需不兼容调整时，提供新的接口版本及迁移说明。

- **数据扩展性要求**：知识数据和映射关系支持新增教材版本、学段、字段和规则；新增字段和历史数据兼容方式由技术方案确定，必要时允许进行可控的数据迁移，不强制预先建设分库分表。

### 4.6 规范性需求

平台的所有设计实现逻辑，必须严格遵循行业标准、公司内部的通用技术标准，以及前端工程化的标准设计规范：

- **标准规范要求**：平台的知识层级结构、元数据属性命名、编码规则，必须严格遵循用户提供的架构设计报告中的相关定义；开放接口的设计必须严格遵循 RESTful API 规范，返回参数的命名规则、数据类型必须统一；数据库的所有表结构、字段命名，必须严格遵循公司内部的统一数据库设计规范。

- **组件规范要求**：优先使用 Ant Design 5.x 或公司现有设计系统的组件；当业务需要时允许使用合适的第三方或自定义组件，但必须满足可访问性、兼容性和统一视觉要求。具体组件选型由 UI/技术设计确定。

- **代码规范要求**：前端工程遵循公司内部前端工程规范；组件目录、状态管理、样式方案和请求工具由技术方案确定。PRD 只要求实现本文件中的页面行为、权限和数据校验，不锁定具体代码目录或样式技术。

- **文档规范要求**：平台的所有技术文档、维护文档，必须采用公司内部的统一文档模板；接口文档必须采用标准化的描述工具，覆盖所有的请求参数、返回参数、示例数据、错误码、调用场景及约束条件；所有的技术文档、维护文档需要归档到公司的统一文档平台，便于后续的查阅和更新。

## 5. 界面原型与交互逻辑说明

本章节描述平台的用户任务、页面信息结构和关键交互；Ant Design、ProLayout、Split、Diff 等具体组件和尺寸由 UI/技术设计确定。本 PRD 不把组件选型、像素值或默认交互当作业务验收条件。

### 5.1 通用布局规范

平台页面采用统一的中后台布局；以下导航和区域划分为建议方案，具体组件、尺寸和响应式细节由 UI 设计稿确定，验收以信息完整、操作可达和关键流程可用为准。

- **布局结构**：页面采用 “顶部导航栏 + 左侧菜单栏 + 主内容区域 + 底部版权栏” 的经典上下结构布局；其中，顶部导航栏高度固定为 64px，左侧菜单栏宽度固定为 200px，主内容区域为撑满式布局，宽度随浏览器窗口的大小自动适配；底部版权栏高度固定为 48px，展示平台的版权信息。

- **布局细节**：
  - 顶部导航栏：从左到右依次展示平台 logo 及名称、一级导航菜单、全局操作工具栏；其中，全局操作工具栏包含入口通知、当前运营人员姓名、退出登录按钮等通用功能项。

  - 左侧菜单栏：展示与当前一级导航菜单对应的二级导航项；菜单需要明确当前选中态、展开和收起状态，具体布局组件和默认行为由 UI/技术设计确定。

  - 主内容区域：采用`PageContainer`组件作为根容器，包裹当前页面的所有核心内容；内容区域的背景色为中后台的标准浅灰色底色，内容卡片的背景色为标准白色；所有的内容区域，都进行了响应式适配设计，在不同分辨率下，自动调整内容的排版布局。

  - 底部版权栏：展示平台的版权信息、当前系统版本号、技术支持联系方式等辅助信息。

- **适配规则**：页面整体适配规则，严格遵循 Ant Design 的官方布局适配规范；主内容区域的最小宽度为 1024px，当浏览器窗口的宽度小于 1024px 时，页面底部将出现水平滚动条；在宽度超过 1440px 的高清设备上，内容区域将按照比例自适应放大，保证信息展示的密度符合用户的视觉体验。

- **栅格规则**：所有页面的内容区域，均采用 Ant Design 的 24 栅格系统进行布局划分；在进行多列布局时，列与列之间的间距（gutter）统一设置为 24px；所有的内容卡片（Card），统一设置为 8px 的圆角、1px 的标准灰色边框，保证视觉效果的统一性。

### 5.2 核心页面原型设计

以下为平台核心页面的详细设计说明，包含页面布局、核心交互逻辑、涉及的 Ant Design 组件及关键视觉属性，所有页面的设计逻辑均遵循 Ant Design 的原生交互规范。

#### 5.2.1 知识树管理页面

知识树管理页面是运营人员维护知识体系的核心入口，承担着五级架构节点维护、原子知识点维护、关联关系及映射关系维护的核心任务；页面布局采用经典的左侧树 + 右侧详情双栏布局，便于运营人员在可视化结构和详情编辑间进行高效切换。

- **页面布局**：
  - 左侧知识树区域：展示完整的五级知识树层级结构，支持搜索、展开、收起和同层级排序；V1 优先一次加载当前教材版本的完整树并使用虚拟滚动，后续数据规模明显增长时再增加按父节点加载子节点的接口。

  - 右侧详情编辑区域：提供“详情编辑”“知识点列表”“映射关系”等维护入口；“映射关系”维护教材位置和政策规则映射，具体标签页和布局由 UI 设计确定。

- **核心交互逻辑**：
  - 知识树的展开 / 收起：用户点击节点名称前的展开 / 收起箭头，可切换该节点下的下级节点显示状态；若节点为四级知识点组节点，展开后将在下级区域展示该节点下的所有原子知识点；若节点为五级原子知识点节点，该节点将不支持展开 / 收起操作。

  - 节点的右键操作：用户右键点击知识树的节点后，将弹出右键菜单，菜单中包含 “新增子节点”“编辑节点”“停用节点”“移动节点”“复制节点” 的快捷操作项；点击操作项后，右侧详情编辑区域将自动切换到对应的编辑状态。

  - 节点的拖拽排序：用户可以点击并拖拽同层级节点，调整节点的排序顺序；在拖拽过程中，系统将在目标位置展示蓝色的拖拽辅助线，用户将节点拖拽到目标位置后，松开鼠标即可完成排序调整；拖拽完成后，系统将自动保存新的排序顺序。

  - 节点选中态同步：用户在左侧知识树区域选中一个节点后，右侧详情编辑区域将自动切换到该节点的详情内容；若该节点为五级原子知识点节点，右侧详情编辑区域将自动展示该节点的所有元数据属性；若该节点为四级知识点组节点，右侧详情编辑区域的知识点列表中将自动展示其下的所有原子知识点。

  - 知识点列表操作：在“知识点列表”标签页中，运营人员可以新增或编辑原子知识点；已被引用的知识点使用“停用/废弃”，不提供硬删除；支持批量映射和批量停用。

  - 表单内容保存：运营人员在右侧详情编辑区域完成内容录入后，点击右下角的 “保存” 按钮，系统将对所有录入字段的合法性进行校验；校验通过后，左侧知识树将自动刷新，展示最新的节点结构或内容。

- **组件细节规范**：页面使用的所有 Ant Design 组件，其核心视觉属性及交互功能均采用官方默认配置或与全局布局规范保持一致，核心组件规范清单如下：

| 区域             | 所用组件       | 功能说明                                       | 视觉 / 交互属性                                                                                 |

#### 5.2.2 发布管理页面

发布管理页面是运营人员将编辑完成的知识内容同步到正式环境的唯一入口，提供发布前内容校验、版本对比、正式发布及发布回滚功能；该页面的核心设计逻辑是 “校验前置、风险可控”，保证只有合法的内容才能被正式发布。

- **页面布局**：采用 Ant Design 的`Card`组件进行垂直布局，从上到下依次为：发布说明编辑区域、更新内容预览区域、发布校验结果区域、操作按钮区域；所有区域的标题和内容左对齐，操作按钮区域采用右对齐布局，让运营人员的视觉流从上到下顺畅贯穿整个页面。

- **核心交互逻辑**：
  - 待发布内容加载：运营人员进入发布管理页面后，系统加载当前编辑空间中未进入正式版本的变更内容；运营人员可按教材版本、节点和变更类型筛选，并将选中内容加入当前发布批次，查看修改前后的详细差异。

  - 发布信息录入：运营人员需要在发布说明编辑区域，录入本次发布的版本号、版本说明、修改原因等核心备注信息；版本号必须采用约定的 “主版本号.次版本号.修订号” 格式，否则系统将自动给出校验提示。

  - 发布前校验：运营人员点击“开始校验”后，系统只校验当前发布批次，检查完整性、合法性、关系、映射、引用和版本冲突；校验结果展示通过项、风险项和错误项，并提供定位到编辑项的入口。

  - 正式发布：若校验结果中存在错误点，运营人员需点击 “返回编辑” 按钮，修改对应的知识内容，重新进行预览和校验；若校验结果只有风险点或完全通过校验，运营人员可以点击 “确认发布” 按钮，系统将弹出二次确认弹窗，运营人员确认后将执行发布操作；发布完成后，系统将在更新内容预览区域展示 “发布成功” 的状态提示，同时记录发布操作的所有日志。

  - 发布回滚：运营人员可以在版本历史管理页面中，找到需要回滚的版本，点击 “回滚到此版本” 按钮；系统将弹出二次确认弹窗，运营人员确认后将执行回滚操作；回滚完成后，系统生成新的正式版本，业务端通过新的 `releaseVersion` 或 `ETag` 重新获取内容，同时记录回滚操作的所有日志信息。

#### 5.2.3 版本历史管理页面

### 5.3 交互规范

为了保证平台的交互体验完整、规范，所有页面的交互逻辑必须严格遵循 Ant Design 的官方交互设计规范；同时，为了降低运营人员的学习成本，平台的所有交互逻辑统一设计，没有任何自定义的特殊交互规则；核心交互规则总结如下：

- **弹窗交互**：简单新增、编辑和确认操作可使用 Modal；字段较多或需要维护映射、关联关系的内容使用详情页或抽屉，避免在小弹窗中承载完整知识点编辑。关闭有未保存内容时必须提示，支持取消、返回和键盘操作。

- **表单交互**：所有的表单提交操作，均需要在前端进行严格的格式校验；校验规则包括必填项校验、格式校验、 range 校验、逻辑关联校验等；只有所有校验项通过后，表单数据才会提交到后端接口；若校验不通过，系统将自动定位到第一个校验失败的表单字段，在字段下方展示红色的校验提示信息，同时将页面滚动到该字段的可视区域内；表单的提交按钮默认处于禁用状态，只有当用户修改了表单内容，且所有校验项都通过后，提交按钮才会变为可用状态。

- **表格交互**：表格支持单条操作和批量操作；批量操作必须展示影响范围和成功/失败结果。分页默认每页 20 条，但允许切换每页数量；列较多时支持横向滚动或列配置，不强制所有字段同时展示。

  - **知识树交互**：单击节点用于选中，展开/收起使用明确的箭头或可访问的展开控件，不依赖双击；支持键盘操作和清晰的选中态。拖拽排序仅用于同层级节点，并在保存前提示变更范围。

  - **批量操作交互**：所有批量操作均需先选择记录并展示影响范围；批量停用、批量移动、批量映射等操作需二次确认，必要时输入确认文案。操作完成后展示成功、失败和跳过数量及逐行错误报告；不提供对正式版本已引用内容的硬删除。

  - **刷新交互**：保存后刷新当前数据区域并保留筛选条件；如果存在未保存内容或并发修改，先提示用户确认，避免自动刷新覆盖编辑内容。批量任务或发布校验使用进度状态，不阻塞整个页面。

- **弹窗返回交互**：所有的弹窗都采用非全屏的模态框设计，不支持超出屏幕宽度的超大尺寸弹窗；在弹窗的内容区域较长、页面出现垂直滚动条时，弹窗的顶部会始终固定在屏幕的垂直居中位置；弹窗的垂直滚动条，仅在弹窗内容区域的高度超过 600px 时才会显示，保证弹窗内容区域的可读性；在关闭弹窗时，系统将自动清空弹窗内的所有表单内容，不会保留上次打开时的录入内容。

- **错误反馈交互**：在后端接口请求失败、表单校验不通过或批量操作部分失败时，展示错误位置、原因、修复建议和 requestId；不在前端展示 Secret、完整签名或完整请求参数。批量操作需提供成功、失败和跳过数量及逐行错误报告；错误提示使用清晰的文字和状态，不只依赖颜色表达。

## 6. 接口设计说明（业务参考）

### 6.1 接口设计原则

知识体系平台的开放接口，是后续业务端获取知识内容的唯一通道，其设计逻辑严格遵循行业标准 RESTful 接口规范，以及公司内部的统一技术要求；保证接口的安全性、兼容性、可扩展性及易用性，降低业务端的接入适配成本。

- **基础设计规范**：
  - 接口传输协议：所有接口均使用 HTTPS；查询使用 GET 或 POST，具体以请求体大小和幂等性为准。内容查询接口为只读接口，所有请求和响应使用 UTF-8 JSON。

  - 数据交互格式：请求和响应统一使用标准 JSON；数组保持 JSON 数组类型，不序列化为字符串；中文和特殊字符按 UTF-8 JSON 传输，不对整个返回值做 URL 编码。

  - 管理端鉴权方式：运营后台使用公司 SSO/OIDC 或受控会话 Cookie 鉴权，前端不保存开放接口 Secret，不在浏览器实现 HMAC 签名。后端通过当前用户信息接口返回角色和权限。

  - 开放接口鉴权方式：后续业务端调用开放只读接口时，采用 AppKey + HMAC 签名机制；业务端传入 AppKey、Signature、Timestamp 和 Nonce，Secret 只保存在服务端，用于对规范化请求方法、路径、时间戳、Nonce 和请求体摘要进行签名校验。平台需要校验时间窗口和 Nonce，防止重放请求。

  - 接口限流规则：每个业务端的接口调用频率，限制为每分钟不超过 1000 次；若超过该阈值，系统将直接拒绝该请求，并在响应中返回 429 状态码，提示 “请求过于频繁，请稍后再试”。

  - 分页参数规范：对于涉及批量数据查询的接口，请求参数中需要包含 pageNum（当前页码）、pageSize（每页显示的记录数）两个分页参数；pageNum 的默认值为 1，pageSize 的默认值为 20，最大值为 100；若请求参数中不包含这两个分页参数，系统将采用默认值进行分页处理。

  - 响应统一结构：HTTP 状态码表达传输和请求结果，业务错误码表达具体业务原因；业务响应统一采用`{"code":"OK","message":"请求成功","data":{},"requestId":"..."}`结构。查询结果需携带发布版本标识，错误响应不得返回 Secret、完整签名或敏感请求参数。

- **版本扩展机制**：为了保证后续的迭代升级，接口的设计采用“端类型路径 + 版本号”的版本控制机制；管理端 V1 路径为`https://{domain}/api/v1/admin/{resource}`，开放端 V1 路径为`https://{domain}/api/v1/open/{resource}`，V2 依次升级为 `/api/v2/admin/...` 和 `/api/v2/open/...`。在新增版本时，旧版本的接口会被保留，不会影响现有业务端的正常调用；业务端可以根据实际需求，自主选择适配的接口版本。

  - **接口粒度设计**：接口按业务场景提供必要字段，支持分页、排序和发布版本过滤；压缩由 HTTP 协商头控制，不额外设计 `compress=1` 业务参数。

### 6.3 错误码规范

接口错误处理同时使用 HTTP 状态码和业务错误码：HTTP 状态码表达传输及通用请求结果，业务错误码用于描述具体业务原因。以下为 V1.0 约定的 HTTP 状态码，业务错误码名称和字段在接口契约文档中统一定义：

| HTTP 状态码 | 描述           | 可能原因                                                 | 处理建议                                                   |
| ------ | -------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| 200    | 请求成功       | 服务器正常处理了请求                                     | 正常处理返回数据                                           |
| 400    | 请求参数错误   | 请求参数格式错误、缺失必填参数或参数取值超出合法范围     | 检查请求参数的格式、必填项及取值范围，修改后重新发起请求   |
| 401    | 鉴权失败       | 管理端会话无效，或开放接口 AppKey/Signature 校验失败       | 检查登录会话或开放接口鉴权信息是否正确 |
| 403    | 被禁止访问     | 当前用户角色或 AppKey 没有调用此接口的权限，或请求资源不允许访问   | 确认当前用户角色或 AppKey 是否有接口权限 |
| 404    | 资源不存在     | 请求的接口地址、`canonical_id` 不存在，或请求的资源已被停用且不在查询版本中   | 检查接口路径和 `canonical_id` 是否正确，确认资源是否存在   |
| 408    | 请求超时       | 服务器处理请求的时间超过了设置的阈值，或网络传输存在延迟 | 检查网络连接是否正常，或稍后重新发起请求                   |
| 429    | 请求过于频繁   | 超过了接口设置的每分钟调用频率阈值                       | 降低接口调用频率，或稍后重新发起请求                       |
| 500    | 服务器内部错误 | 服务器运行异常，未正常处理请求                           | 联系平台技术支持人员，排查后台的详细异常日志               |
| 501    | 服务未实现     | 接口的请求方法不被允许，或不支持该请求路径               | 检查接口的请求方法、请求路径是否正确，修改后重新发起请求   |
| 502    | 网关错误       | 平台的后端服务异常，或网关与后端服务的网络连接异常       | 联系平台技术支持人员，排查后端服务的运行状态               |
| 503    | 服务不可用     | 平台的后端服务正在重启、升级或处于过载状态               | 稍后重新发起请求，或联系平台技术支持人员                   |
| 504    | 网关超时       | 网关与后端服务的网络连接延迟，或后端服务处理时间过长     | 检查网络连接是否正常，或稍后重新发起请求                   |

### 7.1 术语表

为了保证所有参与方对需求文档的理解保持一致，对文档中出现的专属业务名词进行统一的规范定义：

| 术语         | 定义                                                                                                                                                                                                                                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 知识体系     | 支撑 App 所有核心功能的底层结构化知识网络，由 “领域 - 主题 - 单元 - 知识点组 - 原子知识点” 五级层级架构，以及连接原子知识点的前置、后继、平行、交叉等关联关系共同组成；既完整还原教材的章节体例，又补充支撑 App 智能化功能所需的精细化属性，是计算机可识别、算法可匹配、题库可依托的完整结构化知识网络                |
| 五级架构     | 知识体系的核心组织框架，遵循从上到下的逻辑层级划分，依次为一级领域、二级主题、三级单元、四级知识点组、五级原子知识点；这一架构完全锚定人教版教材的编写逻辑，保证了知识体系的规范性与校内适配性                                                                                                                        |
| 原子知识点   | 知识点拆分的最小单元，遵循 “一个教学课时能讲透、不可再拆分” 的拆分标准；是后续知识点匹配、范围判断依据和举一反三训练的最小锚定单元，其拆分逻辑匹配教材的小节教学内容，是整个知识体系的底层基础                                                                                                                        |
| 关联网络     | 连接原子知识点的关系集合，包括前置、后继、平行、交叉四种关系；前置和后继允许跨年级、跨学期，关系用于匹配、补救和推荐，不单独决定题目是否超纲 |
| 公共基础主干 | 用于组织通用知识对象的基础分类和关系模型；教材目录和版本差异通过教材映射关系维护，不将某一版教材目录视为所有版本的固定主干                                                                                 |
| 扩展分支     | 后续教材版本或学段通过新增教材目录、知识对象和映射关系接入；具体复用范围以教研审核和发布前校验结果为准                                                                                                                    |
| 政策规则     | 由官方教育部门或权威教研机构发布的规则及典型问题集合；平台保存规则版本、适用范围、依据和映射关系，供业务端结合题目和学习进度判断                                                                                                                    |
| 开放接口     | 知识体系平台为后续业务端提供的已发布知识内容查询接口，返回教材映射、关联关系、政策规则依据和发布版本信息；题目解析与最终业务决策由业务端完成                                                                                                                                            |
| UI 组件库    | 用于统一页面视觉和基础交互的现有设计系统或组件库；具体组件选型由 UI/技术设计确定，不作为本 PRD 的业务限制                                                   |

### 7.4 待后续迭代内容

由于时间及资源限制，部分无法在 V1.0 版本内实现的需求，将在后续迭代版本中按需开发，主要包括以下内容：

- 完整的多级审核流程：V1.0 提供编辑者维护、发布者确认和系统自动校验；后续可增加教研复核、合规复核等多级审核节点；

- 细粒度角色权限控制：V1.0 保留编辑者、发布者和管理员的最小权限区分；后续根据运营团队分工增加更细的资源和操作权限；

- 多版本教材支持：V1.0 版本仅支持人教版教材的知识内容管理，后续将在扩展分支中，增加其他版本教材（如苏教版、北师大版等）的知识内容适配；

- 知识点批量校验工具：后续将在平台中接入专属的知识点批量校验工具，支持对知识点的元数据、映射关系、关联逻辑进行批量自动校验，提升运营人员的校验效率；

- 第三方题库系统自动同步能力：后续将开发与第三方题库系统的自动同步接口，将知识体系平台的知识点，自动同步到题库系统，完成题目与知识点的映射绑定；

- 完整的操作审计能力：V1.0 已记录关键内容操作、发布、回滚、导入和导出；后续增加审计日志检索、导出和更细的变更字段对比；

- 多语言支持：后续将在平台中增加多语言支持能力，适配不同地区的教材版本及语言需求；

- 知识点图谱可视化编辑：后续将开发完整的知识点图谱可视化编辑功能，支持以可视化方式编辑知识点的关联关系，提升关联关系的维护效率。
